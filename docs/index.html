What is CampusOS?

CampusOS is a cloud-native, multi-tenant School Operating System designed to replace the patchwork of disconnected tools that schools use today. It covers the complete operational surface of a K-12 school: student information, classroom management, scheduling, health records, counselling, library, athletics, transportation, food service, finance, communications, and more — all in one platform with a unified identity model, shared permission framework, and event-driven architecture.

The system is built as a modular monolith (NestJS + Next.js + PostgreSQL + Kafka) with 6 extracted services for compute-intensive workloads (video processing, AI inference, scheduling solver, transport dispatch, notification push, emergency alert). Multi-tenancy uses schema-per-tenant PostgreSQL with a platform schema for shared identity and routing.

Phase 1 (34 cycles, 8 waves) is complete — 418 tables covering every core module, plus observability instrumentation and multi-region disaster recovery. Phase 2 (30 cycles, 4 waves) is in progress — deepening existing modules with .1 cycles and adding new modules (visitor management, incident & emergency, HR depth, events & ticketing, alumni, accreditation) to reach the full 840-table ERD.

Key Architectural Decisions

ADR-001: Soft Cross-Schema Refs

Tenant tables reference platform schema via application-layer validation, not DB-enforced FKs. Enables independent schema evolution.

ADR-008: CQRS-Lite

Domain modules write to operational tables. Background workers materialise read models into rpt_* tables for dashboards and analytics.

ADR-010: Immutable Audit

Audit tables (referral_activity, health_access_log, etc.) have no UPDATE/DELETE at the service layer. Service-side discipline, not schema triggers.

ADR-030: IEP Accommodation Read Model

Teachers read sis_student_active_accommodations populated by Kafka consumer. They never touch hlth_* tables directly.

ADR-055: Universal Person Identity

iam_person is the universal human identity. Domain tables use FK(iam_person) for human refs, FK(platform_users) only for auth/audit.

ADR-057: Platform Event Model

Standard Kafka envelope with event_id, event_type, tenant_id, source_module, correlation_id, payload. All emits follow this shape.

Technology Stack

Backend: NestJS (Node.js 22) · Frontend: Next.js 14 (App Router) + React + Tailwind · Database: PostgreSQL 16 (schema-per-tenant) · Events: Kafka (Redpanda in dev) · Cache: Redis · Monorepo: pnpm workspaces · CI: GitHub Actions · Infra: Docker Desktop (dev), AWS ECS (prod target)
