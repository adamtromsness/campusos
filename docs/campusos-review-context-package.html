CampusOS — Post Phase 2 Review Context Package

For ChatGPT Architectural Review. May 2026. This document summarises the entire CampusOS system built across Phase 1 (34 cycles) and Phase 2 (29 cycles). Use this alongside the ERD v11, Architecture Review, and Function Library for a complete picture.

Your Review Mission: You are reviewing the DESIGN PLANS, not source code. Look for architectural anti-patterns, security concerns, scalability risks, missing error handling patterns, over-engineering, under-specification, and cross-module coupling violations. A separate Claude Code audit will verify actual implementation matches these plans.

1. System Overview

CampusOS is a cloud-native, multi-tenant School Operating System. 840 ERD tables across 38 modules, 76 ADRs. Tech stack: NestJS monolith + 6 extracted services, PostgreSQL (tenant-per-schema), Kafka, Redis, Next.js frontend. ~821 tenant tables built after Phase 2, ~19 deferred to Phase 3.

Key Architectural Patterns

  • Multi-tenancy: Tenant-per-schema with platform schema for cross-tenant entities. Tenant routing via middleware. Schema rebalancing with is_frozen write gate (ADR-031).
  • Identity: iam_person is the universal human FK. platform_users is auth-only. ADR-055 locked.
  • Events: ADR-057 Kafka event envelope (event_id, event_type, event_version, occurred_at, tenant_id, source_module, correlation_id, payload). Topics: {env}.{domain}.{entity}.{verb}. Idempotency via platform_event_consumer_idempotency.
  • Cross-module references: HARD FK within module + to platform. SOFT INTEGRITY across modules (application-layer check). DISPLAY-ONLY for snapshots. No cross-module writes — event-driven propagation only (ADR-028).
  • IMMUTABLE tables: Financial ledger entries, referral activity logs, publication versions, inventory transactions — no UPDATE, no DELETE at service layer.
  • Atomic operations: Ticket sales (UPDATE WHERE qty_sold+$n≤qty), conference slot booking (UPDATE WHERE status='AVAILABLE'), gift card redemption (atomic decrement). Never SELECT-then-UPDATE.

6. Atomic Operation Patterns

  • Ticket sales: UPDATE evt_ticket_tiers SET quantity_sold=quantity_sold+$qty WHERE id=$1 AND quantity_sold+$qty≤quantity — 0 rows = 409 Sold Out
  • Conference booking: UPDATE eng_conference_slots SET status='BOOKED' WHERE id=$1 AND status='AVAILABLE' — 0 rows = 409
  • Gate scanning: UPDATE evt_tickets SET status='USED' WHERE qr_code_token=$1 AND status='VALID' — 0 rows = already scanned
  • Gift card redemption: Atomic decrement current_balance_cents, reject if insufficient
  • Budget transfer: From decremented + to incremented in single transaction
  • Poll voting: UPDATE grp_poll_options SET vote_count=vote_count+1

7. Platform vs Tenant Schema Split

Most tables are tenant-schema (school-scoped). These are platform-schema (cross-tenant):

  • M0 Platform Core: platform_tenants, platform_users, platform_tenant_configs, iam_* tables, schools, districts
  • Officials Marketplace (ADR-063): platform_official_profiles, platform_official_availability
  • Sub Marketplace (ADR-029): platform_substitute_profiles, platform_sub_credentials, platform_sub_availability, platform_sub_preferences
  • Accreditation frameworks (P2-23): platform_accreditation_frameworks, platform_accreditation_standards (platform-seeded, tenant adopts)
  • Publication templates (P2-26): pub_templates with school_id=NULL for system templates

8. Key Design Decisions to Scrutinise

Review these areas specifically:
  1. Election anonymity (P2-28b): ext_votes has NO voter_id column. ext_election_voter_check records WHO voted without linking to HOW. Is structural anonymity sufficient or are there re-identification risks with small electorates?
  2. Engagement scoring (P2-24): Composite score from 5 modules. Are configurable weights + level thresholds appropriate, or does this create a surveillance score?
  3. AI tutoring opt-out (P2-7c): Parent/student opt-out stored in cls_ai_tutoring_opt_outs. Is the opt-out mechanism robust enough? What happens to existing session data on opt-out?
  4. SOFT INTEGRITY everywhere: Cross-module references use application-layer checks, not DB FKs. Is the platform_reference_health monitoring sufficient to catch dangling references?
  5. JSONB for milestone statuses (P2-27): pfl_student_pathway_assignments stores milestone progress as JSONB. Should this be a normalised junction table for queryability?
  6. Tenant-per-schema at scale: 840 tables × N tenants. What's the practical ceiling? How does schema migration work across 100+ tenants?
  7. Financial boundary (M84 vs M83): Payments emits events, Finance consumes and posts GL entries. Is the event contract robust enough for audit-grade financial reconciliation?
  8. Gift card + loyalty (P2-29b): Balance management with atomic decrements. Are there edge cases around concurrent redemptions + top-ups?

10. ChatGPT Review Checklist

Please evaluate each area and provide findings with severity (BLOCKING / IMPORTANT / ADVISORY):
  1. Security: Are there data leakage paths? Can a student see another student's data? Can a parent see non-custody child's data? Are CONFIDENTIAL notes properly restricted? Is PII properly masked in AI pipelines?
  2. Scalability: Which tables will hit scale issues first? Are partitioning strategies correct? Is the trn_vehicle_positions high-frequency write pattern viable? Are materialised read models sufficient?
  3. Data integrity: Are IMMUTABLE constraints enforceable at the DB level (not just service layer)? Are there race conditions beyond the documented atomic operations? Can SOFT INTEGRITY references go stale?
  4. Financial accuracy: Is the M84→M83 event-driven GL posting pattern audit-grade? Can events be lost? What happens on Kafka consumer failure for a payment event?
  5. Operational concerns: Are there tables that will grow unboundedly without retention policies? Are worker frequencies (every minute, nightly, weekly) appropriate? Are DLQ procedures documented?
  6. Over-engineering: Are any modules unnecessarily complex for a school context? Could JSONB columns replace normalised tables in some cases (or vice versa)?
  7. Missing capabilities: Given the 840-table ERD, what critical school operations are NOT covered that a competing SIS would provide?
  8. Privacy/compliance: FERPA, GDPR readiness. Are consent mechanisms adequate? Is the right-to-erasure path viable given IMMUTABLE tables?
