Cycle 27: Procurement

Purchase requisitions with multi-level approval workflow, formal purchase orders to the fin_suppliers directory, budget commitment tracking that reserves funds before payment, goods receipt with inspection and discrepancy logging, automated inventory distribution to 8 operational modules via Kafka events, returns and warranty claims, and vendor performance tracking. The purchasing backbone that feeds every campus operations inventory.
May 2026 · 10 Steps · ERD v11 · M86 Procurement (12 tables — all in scope) · ADR-054/061 · PRC-001 through PRC-003

Plan Overview

Cycle 27 builds the M86 Procurement module — all 12 ERD tables. Per ADR-061, this is the basic procurement scope: requisitions, POs, receiving, distribution, and vendor management. The full procurement scope (three-way matching, blanket POs, catalogue purchasing, encumbrance accounting, competitive bidding) is deferred to Phase 2 per ADR-054, now that Cycle 26 has the GL live to support it.

Procurement is the cross-module supply chain hub. When goods are received and distributed, prc.distribution.completed fires with a destination_module payload. Each destination module's inventory worker consumes the event and creates the appropriate record: tech_assets (IT), trn_parts_inventory (Transportation), fds_inventory (Food Service), lib_catalogue_items (Library), ath_equipment (Athletics), ext_equipment_items (Clubs), fac_supply_inventory (Facilities), str_product_inventory (School Store). Procurement never writes directly to another module's tables.

Vertical Slice Deliverable

Rivera submits a requisition for 10 Chromebooks ($300 each, $3,000 total, destination=tech, budget line=Technology $35K) → wsk_approval_requests routes to department head → department head approves → admin approves → status ADMIN_APPROVED → budget commitment created: fin_budget_lines.encumbered_amount += $3,000, remaining drops by $3,000 → admin converts requisition to PO #2026-047 issued to "Dell Technologies" (from fin_suppliers) → PO issued to vendor → vendor ships → receiving clerk inspects delivery: 10 Chromebooks received, 1 with cosmetic damage → discrepancy logged → admin distributes 9 good units to IT department → prc.distribution.completed fires with destination_module=tech → (future: IT module's worker would create 9 tech_assets rows) → admin initiates a return/warranty claim for the damaged unit → vendor performance score updated (98% quality, 95% on-time) → requisition status walks through to CLOSED.

What's In / What's Deferred

In scope (all 12 tables): prc_requisitions, prc_requisition_lines, prc_purchase_orders, prc_purchase_order_lines, prc_goods_receipts, prc_goods_receipt_lines, prc_budget_commitments, prc_distributions, prc_distribution_lines, prc_returns, prc_vendor_performance, prc_procurement_settings. Functions PRC-001 (Requisitions), PRC-002 (Purchase Orders + Receiving), PRC-003 (Distribution + Returns).

Deferred to Phase 2 (post-M83 full scope per ADR-054): Three-way matching (PO vs receipt vs supplier invoice with tolerance thresholds). Blanket purchase orders (standing orders for recurring purchases). Catalogue-based purchasing (pre-negotiated vendor catalogues). Formal GL encumbrance entries (prc_budget_commitments is the lightweight mechanism; proper encumbrance journal entries are Phase 2). Competitive bidding workflow (RFQ/RFP with vendor comparison scoring). Contract lifecycle management.

Step-by-Step Build Plan

01Requisitions + Lines Schema
Schema

Staff-initiated purchase requests with multi-line item detail, destination module tagging, budget line reference, and integration with the Cycle 7 approval workflow.

Tables (2)
  1. prc_requisitions — school_id UUID, requesting_person_id UUID FK(iam_person) NOT NULL, requesting_department TEXT, urgency TEXT NOT NULL DEFAULT 'ROUTINE' 3-value CHECK (ROUTINE, URGENT, EMERGENCY), status TEXT NOT NULL DEFAULT 'DRAFT' 10-value CHECK (DRAFT, SUBMITTED, DEPT_APPROVED, ADMIN_APPROVED, DISTRICT_APPROVED, ORDERED, RECEIVED, DISTRIBUTED, CLOSED, REJECTED), approval_request_id UUID (soft to wsk_approval_requests), total_estimated_cost NUMERIC(12,2), budget_line_id UUID (soft to fin_budget_lines), justification TEXT NOT NULL, submitted_at TIMESTAMPTZ. INDEX(school_id, status).
  2. prc_requisition_lines — requisition_id UUID FK NOT NULL, item_description TEXT NOT NULL, quantity INT NOT NULL, unit TEXT, estimated_unit_cost NUMERIC(10,2), specifications TEXT, preferred_vendor_id UUID (soft to fin_suppliers), destination_module TEXT NOT NULL 9-value CHECK (tech, trn, fds, lib, ath, ext, fac, str, general). INDEX(requisition_id).
Produces → 2 tables. Migration: 083_prc_requisitions.sql.
02Purchase Orders + Goods Receipt Schema
Schema

Formal POs with sequential numbering issued to fin_suppliers, PO line items linked to requisition lines, goods receipt headers with inspection outcome, and per-line receipt with quantity/condition tracking and discrepancy logging.

Tables (4)
  1. prc_purchase_orders — school_id UUID, po_number TEXT NOT NULL UNIQUE, vendor_id UUID FK(fin_suppliers) NOT NULL, requisition_id UUID FK nullable (POs can be standalone), delivery_address TEXT NOT NULL, expected_delivery_date DATE, payment_terms TEXT, status TEXT NOT NULL DEFAULT 'DRAFT' 8-value CHECK (DRAFT, ISSUED, ACKNOWLEDGED, SHIPPED, PARTIALLY_RECEIVED, RECEIVED, CLOSED, CANCELLED), total_amount NUMERIC(12,2) NOT NULL, issued_by UUID FK NOT NULL, issued_at TIMESTAMPTZ. INDEX(school_id, status).
  2. prc_purchase_order_lines — purchase_order_id UUID FK NOT NULL, requisition_line_id UUID FK nullable, item_description TEXT NOT NULL, quantity_ordered INT NOT NULL, unit_cost NUMERIC(10,2) NOT NULL, line_total NUMERIC(12,2) NOT NULL, gl_account_id UUID (soft to fin_chart_of_accounts for GL coding), destination_module TEXT NOT NULL. INDEX(purchase_order_id).
  3. prc_goods_receipts — purchase_order_id UUID FK NOT NULL, received_by UUID FK NOT NULL, received_at TIMESTAMPTZ NOT NULL, inspection_outcome TEXT NOT NULL 3-value CHECK (ACCEPTED, ACCEPTED_WITH_DISCREPANCY, REJECTED), notes TEXT. INDEX(purchase_order_id).
  4. prc_goods_receipt_lines — receipt_id UUID FK NOT NULL, po_line_id UUID FK NOT NULL, quantity_received INT NOT NULL, quantity_accepted INT NOT NULL, quantity_rejected INT DEFAULT 0, condition TEXT NOT NULL DEFAULT 'GOOD' 3-value CHECK (GOOD, DAMAGED, DEFECTIVE), discrepancy_notes TEXT. INDEX(receipt_id). CHECK(quantity_accepted + quantity_rejected = quantity_received).
Produces → 4 tables. Migration: 084_prc_purchase_orders.sql.
03Budget Commitments + Distribution + Returns + Vendor Performance
Schema

Lightweight budget commitment that reserves funds on PO issuance, distribution records routing received items to destination modules via Kafka events, return/warranty claims, vendor quality + delivery performance scoring, and school-level procurement configuration.

Tables (6)
  1. prc_budget_commitments — purchase_order_id UUID FK NOT NULL, budget_line_id UUID NOT NULL (soft to fin_budget_lines), committed_amount NUMERIC(12,2) NOT NULL, status TEXT NOT NULL DEFAULT 'COMMITTED' 3-value CHECK (COMMITTED, PARTIALLY_RELEASED, RELEASED), released_amount NUMERIC(12,2) DEFAULT 0. On PO ISSUED: committed_amount encumbers the budget line (fin_budget_lines.encumbered_amount += committed_amount). On PO CLOSED: released, encumbered decremented.
  2. prc_distributions — receipt_id UUID FK NOT NULL, distributed_by UUID FK NOT NULL, distributed_at TIMESTAMPTZ NOT NULL, destination_module TEXT NOT NULL 8-value CHECK (tech, trn, fds, lib, ath, ext, fac, str), destination_department TEXT, notes TEXT. Emits prc.distribution.completed per distribution.
  3. prc_distribution_lines — distribution_id UUID FK NOT NULL, receipt_line_id UUID FK NOT NULL, quantity_distributed INT NOT NULL, item_description TEXT NOT NULL, unit_cost NUMERIC(10,2). INDEX(distribution_id).
  4. prc_returns — receipt_line_id UUID FK NOT NULL, return_type TEXT NOT NULL 3-value CHECK (DAMAGED, DEFECTIVE, WARRANTY_CLAIM), quantity_returned INT NOT NULL, return_reference TEXT, vendor_rma_number TEXT, status TEXT NOT NULL DEFAULT 'INITIATED' 4-value CHECK (INITIATED, SHIPPED_TO_VENDOR, RESOLVED, CANCELLED), resolution TEXT nullable 3-value CHECK (REPLACED, REFUNDED, CREDITED) when resolved, initiated_by UUID FK NOT NULL, initiated_at TIMESTAMPTZ.
  5. prc_vendor_performance — vendor_id UUID FK(fin_suppliers) NOT NULL, school_id UUID, total_orders INT DEFAULT 0, on_time_deliveries INT DEFAULT 0, late_deliveries INT DEFAULT 0, accepted_count INT DEFAULT 0, rejected_count INT DEFAULT 0, average_quality_score NUMERIC(3,2), average_delivery_score NUMERIC(3,2), last_updated_at TIMESTAMPTZ. UNIQUE(vendor_id, school_id). Updated on every goods receipt.
  6. prc_procurement_settings — school_id UUID UNIQUE, auto_po_threshold NUMERIC(12,2) nullable (requisitions below this auto-convert to PO without admin approval), default_payment_terms TEXT DEFAULT 'NET_30', po_number_prefix TEXT DEFAULT 'PO', po_number_next_seq INT DEFAULT 1, require_three_quotes_above NUMERIC(12,2) nullable.
Produces → 6 tables. Migration: 085_prc_distribution_vendor.sql. Total Cycle 27 tables: 12.

10Vertical Slice Integration Test
Test
Test Script
  1. Requisition + approval: Rivera submits requisition for 5 iPads (tech, $500 each). Verify wsk_approval_requests entry created. Dept head approves. Admin approves. Status=ADMIN_APPROVED. Verify prc.requisition.submitted fires.
  2. Budget commitment keystone: Convert requisition to PO. On ISSUED: verify prc_budget_commitments row created ($2,500). Verify fin_budget_lines.encumbered_amount incremented by $2,500. Verify remaining_amount decremented.
  3. PO + vendor: PO issued to Apple (fin_suppliers). Verify po_number auto-generated from settings sequence. Verify vendor_id links correctly.
  4. Receiving + inspection: Log receipt: 5 iPads, 4 GOOD + 1 DEFECTIVE. Verify inspection_outcome=ACCEPTED_WITH_DISCREPANCY. Verify prc_vendor_performance updated (quality=80%).
  5. Distribution + Kafka emit: Distribute 4 good iPads to tech. Verify prc.distribution.completed fires with destination_module=tech + 4 items + unit cost.
  6. Return/warranty: Initiate WARRANTY_CLAIM for 1 defective iPad. Status=INITIATED. Ship to vendor. Vendor resolves as REPLACED. Verify resolution recorded.
  7. Vendor performance: Verify vendor scorecard shows: 1 order, 1 on-time delivery, 4 accepted, 1 rejected, quality 80%, delivery 100%.
  8. Requisition rejection: Teacher submits requisition exceeding budget remaining. Verify 400 "Insufficient budget remaining on this line." Teacher submits within budget. Admin rejects with reason. Status=REJECTED.
  9. Visibility: Teacher sees own requisitions + can submit new. Cannot manage POs or receive goods. Admin sees all. Staff (procurement clerk) manages POs + receiving + distribution.
  10. Budget commitment release: Close the PO. Verify commitment status=RELEASED. Verify fin_budget_lines.encumbered_amount decremented. Verify remaining_amount re-increased.
Produces → Verified procurement lifecycle: requisition → approval → PO + budget commitment → receive + inspect → distribute + Kafka → return → vendor score → commitment release.
