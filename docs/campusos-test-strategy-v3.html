CampusOS|Design Hub|TEST STRATEGY v3

Test Strategy v3

Module-by-module DB-backed integration tests. Replaces old mock-based specs. Ordered by criticality. 37 modules across 8 waves. Uses the Tier 0 harness at apps/api/test/integration/.

Replace, don't supplement. Old Wave 3 mock-based specs (21 files under apps/api/src/) are deleted and replaced with DB-backed integration tests as each module is reached. The mock specs validated SQL strings and arg binding — the new tests validate actual DB state, real trigger behavior, real cross-school isolation, and real outbox atomicity. Coverage numbers may temporarily drop for a module during the transition, then exceed the old numbers.

Approach

One Claude Code prompt per module. Each prompt is self-contained: it names the module, lists the test scenarios, specifies the coverage target, and tells Claude Code where to put the files. Run them sequentially — each commits independently.

Test location: apps/api/test/integration/m{XX}-{name}/ mirroring the source module.

Test naming: By business capability, not service class. invoice-lifecycle.spec.ts not invoice.service.spec.ts.

Quality bar (from Codex): Every test seeds real data in tenant_test, calls real service methods, asserts real DB state via raw SQL. Cross-school tests seed School A + B and attempt actual cross-school access. IMMUTABLE tests attempt real UPDATE/DELETE and verify trigger fires. Outbox tests verify the outbox row exists in the same transaction as the domain write.

Coverage Exclusions

These are excluded from vitest coverage measurement (industry standard):

  • **/*.dto.ts — class-validator decorator classes, no executable logic
  • **/*.module.ts — NestJS DI wiring, no executable logic
  • **/index.ts — barrel re-exports

Harness Reference

The Tier 0 integration test harness is built and operational at apps/api/test/integration/. Design doc at docs/operations/procurement-integration-test-harness.md. Key patterns:

  • Schema: tenant_test — provisioned once per suite
  • Isolation: Truncate module tables before each test. Serial execution.
  • Services: new ServiceClass(realDeps) — direct instantiation, no NestJS test module
  • Kafka: RecordingKafkaProducer — captures emit() calls for assertion. No real broker.
  • Fixtures: Shared platform/school/employees/finance fixtures in test/integration/fixtures/. Per-module fixtures created as needed.
  • Commands: pnpm --filter @campusos/api test:integration

Execution Notes

One wave at a time. Each wave is a standalone Claude Code prompt. Run sequentially to avoid git conflicts. Each wave commits independently.

Delete then create. Old mock specs are deleted before new integration tests are written. This prevents confusion about which tests are authoritative.

Coverage may temporarily drop. When old mock specs are deleted and new integration tests are being written, per-module coverage will drop. It recovers (and exceeds) once the wave completes.

Seed data builds cumulatively. Each wave adds fixtures to test/integration/fixtures/. Later waves reuse earlier fixtures. Finance fixtures from Wave 1 are used by procurement in the same wave and by payments consumers in later waves.

Gate: Phase 3 feature builds begin after global combined coverage ≥80%, all financial/auth modules ≥95%, all safety-critical ≥90%.
