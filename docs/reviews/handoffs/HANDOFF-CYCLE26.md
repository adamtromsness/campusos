## What this cycle adds on top of Cycle 25

**Greenfield — clean `fin_*` namespace.** Cycle 26 ships the M83 Finance & Accounting module from scratch. **Opens Wave 6 (Finance & Commerce).**

- **14 new tenant base tables** across 3 migrations (086 + 087 + 088). Tenant base table count after Cycle 25 was 336 → **350** after Cycle 26.
- **1 new backend module** (FinanceModule) with **11 services + 1 controller + 36 endpoints** under `fin-005:read/write/admin` (General Ledger + Chart of Accounts + Periods) + `fin-006:read/write/admin` (Operating Budgets) + `fin-007:read/write/admin` (Accounts Payable) + `fin-008:read/write/admin` (Reconciliation, Board Reports & Grants).
- **1 new Kafka consumer** (`GLConsumer`) on 5 `dev.pay.*` topics (payment.received / invoice.created / refund.issued / credit_note.issued / debt.written_off) — the first Kafka consumer in CampusOS that writes financial data. Idempotency via `fin_journal_batches.source_event_id UNIQUE`.
- **0 new Kafka emit topics** — Cycle 26 is a pure consumer of Cycle 6 `pay.*` events.
- **`validate_batch_balance` primitive lives in `PostingService` rather than as a DB stored function.** The naive `provision-tenant.ts` splitter splits on every `;` without dollar-quote awareness — a CREATE FUNCTION block whose body uses statement terminators would be cut mid-body. The validation runs in service code inside the same `executeInTenantTransaction` callback as the status flip; the integrity guarantee is identical because both paths execute under one transaction and rely on Postgres rollback semantics. See migration 087's closing note for the trade-off + Phase 2 punch-list item to re-introduce the DB function once the splitter is dollar-quote-aware.
- **10 new web routes**: `/finance` (CFO dashboard) + `/finance/accounts` (chart tree) + `/finance/journals` (GL viewer with post/void) + `/finance/trial-balance` + `/finance/periods` (status pills + LOCK warning) + `/finance/budgets` (variance dashboard) + `/finance/ap` (voucher queue) + `/finance/reconciliation` + `/finance/board-reports` + `/finance/grants`.
- **Permission codes:** 4 NEW catalogue entries — `FIN-005` (General Ledger & Chart of Accounts), `FIN-006` (Operating Budgets), `FIN-007` (Accounts Payable), `FIN-008` (Reconciliation, Board Reports & Grants). Catalogue grew **454 → 465** (4 functions × 3 tiers). The pre-existing `FIN-001..004` codes (Family Billing / Financial Aid / Fundraising / Budget Management) are NOT reused — `FIN-001:read+write` is held by parents from Cycle 6 family billing, so reusing it for the GL surface would leak finance access to parents at the controller gate. Phase 2 punch-list item: rename `FIN-001..004` → `BIL-001..004` (Family Billing) and free the `FIN-*` namespace for the GL family.

**Three structural keystones for the cycle:**

1. **Service-validated double-entry posting (ADR-058 / ADR-059 KEYSTONE).** `fin_journal_batches.status` flips DRAFT → POSTED only after PostingService writes all `fin_gl_entries` lines AND runs an in-transaction `SUM(debit), SUM(credit), COUNT(*)` validation that throws on imbalance — the entire `executeInTenantTransaction` callback rolls back and no half-posted batch can land. Application header totals are not trusted; only the actual rows aggregated inside the same tx as the status flip count.

2. **Permanent period LOCK.** `fin_accounting_periods.status` lifecycle FUTURE → OPEN → CLOSED → LOCKED. **LOCKED is irreversible at the service layer** — `PeriodService.patchStatus` refuses any transition out of LOCKED, regardless of caller. The PostingService refuses any entry where the target period is CLOSED or LOCKED. Not even Platform Admin can override — the locked-period invariant is part of the financial integrity contract.

3. **Idempotent GL Consumer (Cross-cycle keystone).** `GLConsumer` subscribes to 5 `dev.pay.*` topics from Cycle 6 (M84 Family Billing) under group `gl-consumer`. Per inbound event: resolves the chart of accounts mapping, constructs a balanced journal batch (e.g., `pay.payment.received` → DEBIT Cash + CREDIT Tuition Revenue), calls `PostingService.createAndPost(...)` with the Kafka `event_id` as `sourceEventId`. The partial UNIQUE INDEX on `fin_journal_batches.source_event_id WHERE NOT NULL` provides idempotency — a redelivered Kafka event finds the existing batch and the helper returns it without re-posting. **Verified live end-to-end on `tenant_demo` 2026-05-06**: parent pays $30 invoice via `/invoices/:id/pay` → Cycle 6 emits `pay.payment.received` envelope → GLConsumer auto-posts AUTO-019DFF45 batch (DEBIT Cash $30 / CREDIT Tuition $30) — POSTED with source_module='payments' + source_event_id populated; consumer log line `[gl-consumer] posted batch AUTO-019DFF45 (019dff45) from pay.payment.received eventId=019dff45` captured. Activates the M84→M83 integration contract that has been designed since Wave 1.

**Existing-system touchpoints:**

- `pay_payments` / `pay_invoices` / `pay_refunds` (Cycle 6) — soft `reference_type` + `reference_id` on `fin_gl_entries` lets a posted batch link back to the originating payment / invoice / refund row. The Kafka consumer reads the originating ids from the `pay.*` envelope payload.
- `hr_employees(id)` — DB-enforced FK on `fin_journal_batches.posted_by`, `fin_ap_vouchers.approved_by`, `fin_ap_payments.paid_by`, `fin_reconciliation_runs.reconciled_by`, `fin_board_report_snapshots.generated_by` with `ON DELETE SET NULL` to preserve audit when an employee leaves.
- `wsk_approval_requests(id)` (Cycle 7) — soft `approval_request_id` column on `fin_ap_vouchers` for future workflow integration (vouchers above a threshold route through the approval engine).

What does not change: every existing module continues to function. Cycle 26 is purely additive on a clean `fin_*` namespace. The Cycle 6 `pay.*` emits already fire — Cycle 26 just adds a consumer.

## Step 6 — PostingService + GLConsumer (DOUBLE-ENTRY KEYSTONE)

`apps/api/src/finance/posting.service.ts` ships `PostingService` with 6 endpoints under fin-005:read/write/admin (list with status + periodId + sourceModule filters; getById; createDraft + post + void + createAndPost public helper). **`post(id)` is the ADR-058/ADR-059 keystone** — wraps in `executeInTenantTransaction`, locks the batch row + parent period with `SELECT … FOR UPDATE OF b`, refuses already-POSTED + already-VOIDED + CLOSED/LOCKED period, calls private `validateBalance(tx, batchId)` which aggregates `SUM(debit), SUM(credit), COUNT(*)` and throws on imbalance (whole tx rolls back), flips status to POSTED + stamps `posted_at`+`posted_by`, then UPDATEs every `fin_budget_lines.actual_amount` whose account_id matches a posted GL entry's account using `CASE WHEN normal_balance='DEBIT' THEN SUM(debit) ELSE SUM(credit) END`. `createAndPost` is the GLConsumer's idempotent helper — checks `source_event_id UNIQUE` first (returns existing batch on Kafka redelivery), auto-resolves the OPEN period covering today when `periodId` is omitted, runs the same validation+post+budget-update pipeline. `void(id, reason)` is admin-only — flips POSTED → VOIDED + stamps `voided_at`+`voided_by`+`void_reason` + reverses budget actuals via `GREATEST(actual_amount - delta, 0)`. **`apps/api/src/finance/gl.consumer.ts` ships `GLConsumer`** subscribed to all 5 `dev.pay.*` topics under group `gl-consumer`.
