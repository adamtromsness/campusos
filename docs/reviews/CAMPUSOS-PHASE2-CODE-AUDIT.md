### Category 5 — Atomic Operation Verification: **7/7 ATOMIC**

All 7 documented patterns confirmed atomic via inline SQL extraction:

1. **Ticket sales** (`orders.service.ts:312-315`) — `UPDATE evt_ticket_tiers SET quantity_sold = quantity_sold + $1 WHERE id = $2 AND quantity_sold + $1 <= quantity RETURNING …` — single-statement.
2. **Conference booking** (`conference-booking.service.ts:315-326`) — `UPDATE eng_conference_slots SET current_bookings = current_bookings + 1, status = CASE … END WHERE … AND status='AVAILABLE' AND current_bookings < max_bookings RETURNING …` — single-statement, school-scoped.
3. **Gate scanning** (`gate.service.ts:111-117`) — `UPDATE evt_tickets SET status='USED', scanned_at=now() WHERE … AND qr_code_token=$2 AND status='VALID' RETURNING …` — single-statement.
4. **Gift card redemption** (`gift-card.service.ts:290-309`) — All gates in WHERE (balance + expiry + status + school-scope). `status = CASE WHEN balance - $1 = 0 THEN 'DEPLETED' …` atomic depletion flip.
5. **Budget transfer** (`budget-transfer.service.ts:213-289`) — Three-step locked-tx; both budget rows locked in deterministic id-ascending order (deadlock-safe).
6. **Promotion max_uses** (`promotion.service.ts:392-409`) — `WHERE … AND (max_uses IS NULL OR current_uses < max_uses)` — single-statement.
7. **Journal batch post** (`journal-batch.service.ts:328-385`) — `FOR UPDATE` lock + fresh SUM re-aggregation under lock + tolerance check (`|d-c| <= 0.005`).

No SELECT-then-UPDATE race patterns found.
