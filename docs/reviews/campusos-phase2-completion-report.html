Merged Findings — Deduplicated & Prioritised

Where both reviewers flagged the same issue, the higher severity is used. Source attribution shows which reviewer(s) identified it.

IMPORTANT Findings (11)

IMP-01 — Custody-Aware Parent Access Must Be Centralised
Claude P-02 (advisory) + ChatGPT SEC-01 (important) → elevated to IMPORTANT

Multiple parent-facing surfaces (health, engagement, college apps, payments, conferences, portfolio, transport) check parent access independently. Custody arrangements, court orders, safety restrictions, and per-capability permissions must not be reimplemented per module.

Action: Create a central GuardianAuthorizationService with capability-specific methods (canViewAcademicRecord, canViewHealthRecord, canAuthorizePayment, canReceiveTransportInfo, canAttendConference). Policy-backed, audited, reused by all modules.

IMP-02 — IMMUTABLE Tables Need DB-Level Enforcement
Claude I-01 + ChatGPT DI-01 → both IMPORTANT

All 7+ IMMUTABLE tables are enforced at the service layer only. A developer with direct DB access or a migration script could violate immutability. Both reviewers flagged this identically.

Action: For every IMMUTABLE table: (1) Postgres BEFORE UPDATE OR DELETE trigger that raises exception. (2) Remove UPDATE/DELETE grants from application DB role. (3) Break-glass maintenance path with dual approval + audit. (4) CI test that attempts UPDATE/DELETE and expects failure.

IMP-03 — AI PII Masking & Deletion Policy Under-Specified
ChatGPT SEC-02 → IMPORTANT (Claude did not flag)

The AI Gateway is architecturally correct as a choke point, but operational rules are undefined: prompt retention, provider logging, deletion on opt-out, reprocessing rules, special treatment for health/behaviour/counselling data. What happens to existing AI tutoring session data when a parent opts out?

Action: Define an AI Data Policy covering: PII minimisation before model calls, stable pseudonym replacement, provider retention settings, opt-out effect on historical artifacts, deletion/pseudonymisation path for DPO requests, special rules for sensitive data categories.

IMP-04 — Tenant-per-Schema Migration Model at 100+ Tenants
ChatGPT SCL-01 → IMPORTANT (Claude did not flag)

840 tables × N tenants means long-running migration windows, partial failures, and schema drift. The ERD mentions is_frozen write gate for rebalancing, but the production migration orchestration is not specified.

Action: Define migration orchestration standard: max tenants per cluster, canary tenant strategy, resumable execution, expand/contract DDL pattern, online index creation rules, schema drift verification, failure rollback procedure.

IMP-05 — High-Volume Table Retention & Partitioning Enforcement
Claude S-02 (advisory) + ChatGPT SCL-02 (important) → elevated to IMPORTANT

trn_vehicle_positions (~1.7M rows/day for 200 buses), msg_messages (potentially 250M rows/month), evt_ticket_scans, audit logs, and Kafka outbox tables all need verified partition creation, retention jobs, and failure alerts.

Action: For each high-volume table: verify partition creation is automated, retention drop job exists, failure alerting is configured, archive policy is documented. Claude Code audit should confirm actual implementation.

IMP-06 — Soft-Integrity Drift Monitoring
ChatGPT DI-02 → IMPORTANT (Claude flagged pattern but not monitoring)

SOFT INTEGRITY references across modules will inevitably go stale (deleted records in source module leave dangling references in consumer module). No monitoring or repair workflow is specified.

Action: Build a platform_reference_health scanning job that checks all soft-reference categories nightly, reports dangling counts, and triggers repair workflows (hide stale display-only refs, quarantine invalid workflow records, rehydrate read models).

IMP-07 — GL Reconciliation Controls
ChatGPT FIN-01 → IMPORTANT (Claude confirmed chain complete but didn't flag reconciliation)

Event-driven GL posting is audit-grade only if completeness is provable. Currently no reconciliation job verifies that every pay_invoice, payment, credit_note, and reversal has corresponding GL entries.

Action: Build daily reconciliation jobs: every payment source event → expected GL entry exists. Every source_event_id → at most one posted batch. DLQ payment events are finance-blocking incidents with SRE escalation.

IMP-08 — Kafka DLQ Runbooks & Replay Procedures
ChatGPT OPS-01 → IMPORTANT (Claude did not flag)

Kafka is used heavily but consumer retry policy, DLQ triage, replay ordering, poison-message quarantine, and financial event escalation SLAs are not specified in the design package.

Action: Create Kafka operations runbook: retry policy by event class, DLQ naming/payload format, alert thresholds by criticality, replay procedure with idempotency verification, poison-message quarantine workflow, financial/safety event escalation SLAs.

IMP-09 — Right-to-Erasure vs Immutable Records
ChatGPT COMP-01 → IMPORTANT (Claude did not flag at plan level)

GDPR Article 17 right-to-erasure conflicts with IMMUTABLE financial, referral, and audit tables. The DPO module is deferred to Phase 3, but production launch before defining the retention/pseudonymisation policy is risky. The ERD does include a dpo_pseudonymisation_log table, but the operational workflow is undefined.

Action: Define retention/pseudonymisation matrix by record class before pilot: GL entries (pseudonymise, don't delete), referral activity (pseudonymise), AI transcripts (delete on request), analytics (recompute without PII), health logs (pseudonymise with legal basis). The DPO module can remain Phase 3, but the policy must be documented now.

IMP-10 — Engagement Score Treated as Sensitive Profiling
Claude D-03 (advisory) + ChatGPT COMP-02 (important) → elevated to IMPORTANT

Composite family engagement scores from 5 data sources (attendance, communications, conferences, volunteering, payments) risk becoming a general-purpose family ranking metric used for admissions, discipline, or financial aid decisions.

Action: Restrict component-level view to engagement_admin permission only. Exclude from data exports by default. Prohibit use in admissions/discipline/financial aid decisions (enforce via policy, not just documentation). Store weight version with every score. Allow schools to disable payment-derived weighting entirely.

IMP-11 — Student-Owned Data Enforcement Inconsistent
Claude P-01 → IMPORTANT

Multiple cycle plans declare data as "student-owned" (reflections, portfolios, recruiting profiles, resume) but the enforcement mechanism varies. The coach delegation exception in recruiting profiles is under-specified.

Action: Claude Code audit must verify every "student-owned" table has student_id = req.user.personId guard. Coach delegation should use a formal delegation pattern (not role === 'COACH'). Create a shared @StudentOwned decorator for consistent enforcement.

ADVISORY Findings (8)

ADV-01 — Kafka Events With No Documented Consumer
Claude K-01 + ChatGPT OPS-02

6 events emitted with no consumer: eng.conference.booking_open, eng.survey.opened, lib.import.completed, pub.publication.published, trn.parts.low, fds.inventory.low. Classify each as: notification trigger (add Comms consumer), future automation (document backlog owner), or observable-only (no consumer needed).

ADV-02 — JSONB Milestone/Status Fields Need Read Models
Claude D-01 + ChatGPT DI-03

JSONB columns for milestone_statuses, follow_up_actions, action_plans hard to query at school-wide dashboard scale. Add materialised read models (rpt_pathway_milestone_completion, etc.) without prematurely normalising the checklist view.

ADV-03 — Nightly Worker Thundering Herd
Claude S-01 + ChatGPT SCL-03

At 100+ tenants, all nightly workers firing simultaneously creates DB contention. Use per-tenant jitter: nightly within 2-hour window, weekly random day/hour, heavy recompute queue-based with concurrency limits.

ADV-04 — Election Small-Electorate Re-Identification
ChatGPT SEC-03

Structural anonymity (no voter_id on ext_votes) is correct, but with 1 voter the outcome is trivially identifiable. Suppress or aggregate results until min_votes threshold (e.g., 5) is met.

ADV-05 — prc.distribution.completed Consumer Coverage
Claude K-02

ERD documents 8 module consumers for distribution events but not all modules have inventory receipt handlers built. Claude Code audit should verify which consumers actually exist.

ADV-06 — TEXT+CHECK Pattern Should Be Documented as ADR
Claude D-02

Consistent use of TEXT with CHECK constraints instead of Postgres ENUMs is correct for extensibility but should be formally documented so future developers don't "fix" it.

ADV-07 — Complexity Hidden Behind School-Size Defaults
ChatGPT ENG-01

All features included (no gating) is correct commercially, but micro/small schools will be overwhelmed. Use configuration presets (Micro, Small, Advanced) that surface features progressively, not feature gates.

ADV-08 — Production Readiness Prioritisation
ChatGPT CAP-01

Domain coverage is broad; gaps are operational. Priority order for Phase 3: (1) Data import pipeline, (2) DPO/erasure workflow, (3) Full finance/AP, (4) Notification push service, (5) Scheduling solver, (6) Transport dispatch.

Final Summary

CampusOS Phase 2 is architecturally complete: 821 tenant tables across 38 modules, ~2,000 endpoints, 63 build cycles. Both independent reviewers agree the design is sound and internally consistent. The 11 IMPORTANT findings are governance and hardening issues, not architectural flaws. The P1 items (DB immutability triggers, custody guard, student-owned enforcement, engagement score restrictions, GL reconciliation) are estimated at ~6–8 days of Claude Code work. The P2 items are primarily policy documents + operational tooling. Phase 3 can begin in parallel with pre-production hardening.
