Cycle 28: School Store

Dual-mode school store: a STUDENT store with parent approval before checkout and family account billing, and a PUBLIC store for external customers with shipping. Product catalogue with SKU management and multi-location inventory, order lifecycle with backorder support, automatic procurement reorder when inventory hits threshold, revenue tracking materialised by StoreRevenueWorker, and the str.order.completed Kafka emit that Cycle 6's payment module consumes. Closes Wave 6.
May 2026 · 10 Steps · ERD v11 · M67 School Store (9 tables — all in scope) · ADR-062 · STR-001 through STR-003 · Closes Wave 6

Plan Overview

Cycle 28 builds the M67 School Store module — all 9 ERD tables. Per ADR-062, the store has two modes: a STUDENT store where students browse and order (uniforms, PE kits, textbooks, school supplies) but every order requires parent approval before payment is charged to the family account, and a PUBLIC store where external visitors (alumni, community members) can purchase school merchandise with shipping and direct payment.

The module sits at the intersection of 3 prior cycles: Cycle 6 Payments (the store emits str.order.completed; M84 consumes it to charge the family account — the store never writes to pay_ tables), Cycle 27 Procurement (when inventory falls below reorder_point, the system can auto-generate a prc_requisition), and Cycle 26 Finance (str_store_revenue is a materialised read model that feeds into the financial reporting layer). The parent approval gate is the fifth parent-active feature.

Vertical Slice Deliverable

Admin creates a STUDENT store "Lincoln Academy Shop" + a PUBLIC store "Eagle Merchandise" → adds products: School Polo ($25, SKU: POLO-BLU-M, category: Uniform), PE Kit ($35, SKU: PE-KIT-S), Yearbook ($20, SKU: YRB-2026), Eagle Hoodie ($45, SKU: HDY-GRY-L, PUBLIC store) → sets inventory: 50 Polos, 30 PE Kits, 100 Yearbooks, 25 Hoodies → Maya (student) browses the STUDENT store, adds 1 Polo + 1 Yearbook to her order → order status=PENDING_APPROVAL → David Chen (parent) receives notification, approves → order advances to PROCESSING, payment charged to family account via str.order.completed → staff fulfils → status=READY_FOR_PICKUP → Maya picks up → COMPLETED → inventory decrements (49 Polos, 99 Yearbooks) → meanwhile, an alumni visits the PUBLIC store, orders 2 Eagle Hoodies ($90 + $5 shipping), pays by card → order SHIPPED with tracking → PE Kit inventory drops to 5 (at reorder_point), triggering a procurement reorder signal → StoreRevenueWorker materialises: April total $170 revenue, $85 cost, $85 margin.

Step-by-Step Build Plan

01Stores + Products + Inventory Schema
Schema

Dual-mode store registry (STUDENT + PUBLIC), product catalogue with SKU + category + cost tracking + image support, and multi-location inventory with reorder thresholds.

Tables (3)
  1. str_stores — school_id UUID NOT NULL, store_type TEXT NOT NULL 2-value CHECK (STUDENT, PUBLIC), name TEXT NOT NULL, description TEXT, is_active BOOLEAN DEFAULT true. UNIQUE(school_id, store_type). One STUDENT store + one PUBLIC store per school.
  2. str_products — store_id UUID FK NOT NULL, name TEXT NOT NULL, description TEXT, sku TEXT, category TEXT, price NUMERIC(8,2) NOT NULL, cost NUMERIC(8,2), image_s3_keys TEXT[], is_active BOOLEAN DEFAULT true, backorder_allowed BOOLEAN DEFAULT false. INDEX(store_id, category, is_active).
  3. str_product_inventory — product_id UUID FK NOT NULL, location_type TEXT NOT NULL 2-value CHECK (BUILDING, DISTRICT), location_id UUID NOT NULL, quantity_on_hand INT DEFAULT 0, quantity_reserved INT DEFAULT 0, reorder_point INT DEFAULT 0, reorder_quantity INT DEFAULT 0. UNIQUE(product_id, location_type, location_id). When quantity_on_hand ≤ reorder_point: signal for procurement reorder.
Produces → 3 tables. Migration: 086_str_stores_products.sql.
02Orders + Lines + Approvals Schema
Schema

Order headers with customer polymorphism (internal person OR external customer), per-line item tracking with backorder support, and the parent approval gate for student orders.

Tables (3)
  1. str_orders — store_id UUID FK NOT NULL, order_type TEXT NOT NULL 3-value CHECK (STUDENT, PARENT, EXTERNAL), customer_person_id UUID (soft to iam_person; for STUDENT/PARENT orders), external_customer_id UUID FK nullable (for EXTERNAL orders), student_id UUID (soft to sis_students; for STUDENT orders — the student who will receive the items), order_date TIMESTAMPTZ NOT NULL, status TEXT NOT NULL 8-value CHECK (PENDING_APPROVAL, APPROVED, PROCESSING, READY_FOR_PICKUP, SHIPPED, COMPLETED, CANCELLED, BACKORDERED), subtotal NUMERIC(10,2), shipping_cost NUMERIC(8,2) DEFAULT 0, total NUMERIC(10,2), shipping_method TEXT DEFAULT 'PICKUP' 2-value CHECK (PICKUP, SHIPPED), payment_status TEXT DEFAULT 'PENDING' 4-value CHECK (PENDING, CHARGED, DEFERRED_BACKORDER, REFUNDED). INDEX(store_id, status). INDEX(customer_person_id) WHERE customer_person_id IS NOT NULL.
  2. str_order_lines — order_id UUID FK NOT NULL, product_id UUID FK NOT NULL, quantity INT NOT NULL, unit_price NUMERIC(8,2) NOT NULL, line_status TEXT DEFAULT 'IN_STOCK' 4-value CHECK (IN_STOCK, BACKORDERED, FULFILLED, CANCELLED). INDEX(order_id).
  3. str_order_approvals — PARENT APPROVAL GATE. order_id UUID FK NOT NULL UNIQUE, parent_person_id UUID NOT NULL (soft to iam_person), status TEXT NOT NULL DEFAULT 'PENDING' 3-value CHECK (PENDING, APPROVED, DECLINED), requested_at TIMESTAMPTZ NOT NULL, responded_at TIMESTAMPTZ, decline_reason TEXT. On APPROVED: order advances to PROCESSING, payment charged. On DECLINED: order CANCELLED, inventory released.
Produces → 3 tables. Migration: 087_str_orders.sql.
03External Customers + Shipping + Revenue Schema
Schema

Non-CampusOS customer records for the public store, shipping method options with flat-rate pricing, and materialised periodic revenue summaries.

Tables (3)
  1. str_external_customers — name TEXT NOT NULL, email TEXT NOT NULL, phone TEXT, shipping_address TEXT. INDEX(email). Non-CampusOS users who purchase from the PUBLIC store.
  2. str_shipping_options — store_id UUID FK NOT NULL, method_name TEXT NOT NULL, estimated_days INT, flat_rate NUMERIC(8,2) NOT NULL, is_active BOOLEAN DEFAULT true. INDEX(store_id, is_active). Only applies to PUBLIC store orders with shipping_method=SHIPPED.
  3. str_store_revenue — Materialised by StoreRevenueWorker. store_id UUID FK NOT NULL, period_start DATE NOT NULL, period_end DATE NOT NULL, total_orders INT, total_revenue NUMERIC(12,2), total_cost NUMERIC(12,2), gross_margin NUMERIC(12,2). UNIQUE(store_id, period_start, period_end).
Produces → 3 tables. Migration: 088_str_external_shipping.sql. Total Cycle 28 tables: 9.

05Products + Inventory NestJS Module
Code
Services & Endpoints
  1. StoreService — GET /store/stores (returns STUDENT store for authenticated internal users; PUBLIC store for all), POST /store/stores (admin creates), PATCH /store/stores/:id.
  2. ProductService — GET /store/stores/:id/products (catalogue browse with category filter; only is_active products), GET /store/products/:id (with inventory inlined), POST /store/products, PATCH /store/products/:id.

06Orders + Approvals NestJS Module
Code
Services & Endpoints
  1. OrderService — POST /store/orders (DUAL-MODE KEYSTONE: STUDENT orders auto-create str_order_approvals row with status=PENDING + reserve inventory; PARENT orders charge family account directly; EXTERNAL orders require external_customer_id + shipping_option_id). GET /store/orders (student: own; parent: child's; admin: all), GET /store/orders/:id. PATCH /store/orders/:id/fulfil (staff: PROCESSING → READY_FOR_PICKUP or SHIPPED), PATCH /store/orders/:id/complete (READY_FOR_PICKUP → COMPLETED; decrements inventory; emits str.order.completed), PATCH /store/orders/:id/cancel (releases reserved inventory). Backorder: if product.backorder_allowed and insufficient stock, line_status=BACKORDERED, payment_status=DEFERRED_BACKORDER.
  2. ApprovalService — GET /store/approvals (parent: pending approvals for my children), PATCH /store/approvals/:id/approve (parent approves → order advances to PROCESSING; emits str.order.completed for family account billing), PATCH /store/approvals/:id/decline (parent declines → order CANCELLED, inventory released).
Produces → 2 services, ~10 endpoints, 2 Kafka emits (str.order.completed + str.inventory.reorder_needed).

10Vertical Slice Integration Test
Test
Test Script
  1. Store setup: Admin creates STUDENT + PUBLIC stores. UNIQUE(school_id, store_type) enforced. Adds 4 products to STUDENT store + 2 to PUBLIC store with inventory.
  2. Student order + parent approval: Maya orders 1 Polo + 1 Yearbook ($45). Status=PENDING_APPROVAL. Inventory reserved (quantity_reserved += quantities). David approves. Status→PROCESSING. str.order.completed fires. Verify payment_status=CHARGED.

  4. Fulfilment + inventory: Staff fulfils Maya's order → READY_FOR_PICKUP. Maya picks up → COMPLETED. Verify quantity_on_hand decremented (49 Polos, 99 Yearbooks).
  5. External order + shipping: Alumni creates external customer record. Orders 2 Hoodies from PUBLIC store with Standard Shipping. Total=$95. Staff ships with tracking number. Status=SHIPPED→COMPLETED.
  6. Backorder: Product with 0 stock + backorder_allowed=true. Student orders. Verify line_status=BACKORDERED, payment_status=DEFERRED_BACKORDER. When stock arrives (inventory adjusted), line_status→IN_STOCK.
  7. Reorder threshold: Adjust PE Kit inventory to reorder_point (5). Verify str.inventory.reorder_needed fires.
  8. Revenue materialisation: Trigger StoreRevenueWorker. Verify str_store_revenue reflects completed orders: correct total_orders, total_revenue, total_cost, gross_margin.
  9. Visibility: Student sees STUDENT catalogue + own orders. Cannot see PUBLIC store admin. Parent sees approval queue + child's order history. External customer can only access PUBLIC storefront. Staff manages fulfilment + products. Admin sees all.
  10. Cross-module: Verify str.order.completed payload matches the contract M84 expects (family_account_id, amount, line items). Verify str.inventory.reorder_needed payload includes product + quantity + preferred supplier for procurement bridge.
