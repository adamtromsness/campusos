Plan Overview

Cycle 31 is the first of two hardening cycles in Wave 8. Unlike every prior cycle which added new domain tables and endpoints, this cycle adds zero new business tables. Instead, it instruments, optimises, and stress-tests the ~418 tables and ~936 endpoints built across 30 prior cycles. The deliverable is not a feature — it is the confidence that the platform can handle a real school district's load before pilot.

The cycle spans 4 domains: (1) observability infrastructure — structured logging, distributed tracing, metrics export, and the alerting pipeline, (2) performance baselines — load testing critical hot paths, query optimisation from pg_stat_statements, and establishing p50/p95/p99 latency baselines, (3) data infrastructure — partition activation for high-volume tables, PgBouncer schema-per-tenant tuning, and Redis caching, and (4) operational resilience — DLQ dashboard, consumer envelope validation, circuit breakers, transactional outbox evaluation, and error budget SLOs.

Architecture — External Observability Stack

CampusOS does NOT store its own operational metrics in its own database. The observability stack is external: CloudWatch/ELK for logs, Prometheus + Grafana for metrics, OpenTelemetry + Jaeger/X-Ray for tracing, PagerDuty/Slack for alerting. This avoids the circular dependency where a database problem prevents you from seeing that there's a database problem. The only internal observability surface is platform_kafka_consumer_health (already exists from Cycle 0) and the DLQ dashboard wired this cycle.

Step-by-Step Build Plan

01Structured Logging + Correlation IDs
Ops

Enforce the structured log schema from Section 25.2 of the Architecture Review across every NestJS module, Kafka consumer, and background worker.

Deliverables
  1. Log schema validation linter: CI lint rule that fails the build if any log line is missing required fields (timestamp, level, service_name, trace_id, span_id, tenant_id, message). Checks for prohibited content: stack traces in message field, PII in any field (names, emails — only IDs allowed).
  2. Trace ID propagation middleware: NestJS global middleware generates a UUIDv7 trace_id on every incoming HTTP request (or accepts X-Trace-Id from upstream). Propagates through all internal service calls via X-Trace-Id header, all Kafka emits via ADR-057 correlation_id field, all DB queries via query comments (/* trace_id=... tenant_id=... */), all log entries.
  3. Structured JSON log format: Replace any remaining console.log calls with the structured logger. Required fields: timestamp (ISO 8601 UTC), level, service_name, trace_id, span_id, tenant_id, message. Conditional: user_id, event_type (on consumer log lines), worker_name, duration_ms, error_code, module prefix.
  4. Log aggregation config: CloudWatch Logs sink configuration. Log group per service. Retention: 90 days hot, 1 year cold.
Produces → Every log line across all 30+ modules is structured JSON with trace_id. CI enforced.
02OpenTelemetry Distributed Tracing
Ops

Instrument the entire request lifecycle with OpenTelemetry spans so a single trace_id reconstructs the full operation from HTTP request through database query through Kafka emit through consumer processing.

Deliverables
  1. OTel SDK integration: @opentelemetry/sdk-node configured in the NestJS bootstrap. Auto-instrumentation for HTTP (incoming + outgoing), PostgreSQL (pg driver), Redis (ioredis), and Kafka (kafkajs). Backend: Jaeger (dev) or AWS X-Ray (prod).
  2. Service boundary spans: New spans created at every module service entry point. Parent span from HTTP request. Child spans for each DB query, Redis operation, Kafka produce, and external service call (AI Gateway, push providers, Stripe).
  3. Kafka consumer tracing: On message consume: extract correlation_id from the ADR-057 envelope, create a new span linked to the original trace. Consumer processing duration captured as span attribute.
  4. Cross-service propagation: When the monolith calls an extracted service (Video Processing, Scheduling Solver, etc.), trace_id + span_id passed in headers. Extracted service creates child spans under the same trace.
Produces → End-to-end distributed tracing across HTTP → service → DB → Kafka → consumer → extracted service.
03Prometheus Metrics + Grafana Dashboards
Ops

Export platform metrics via Prometheus and build the Grafana dashboards that the SRE team uses for capacity planning and incident response.

Deliverables
  1. /metrics endpoint: Prometheus-compatible metrics export from the NestJS application. Histograms: http_request_duration_seconds (by route, method, status_code), db_query_duration_seconds (by module), kafka_produce_duration_seconds. Gauges: kafka_consumer_lag (by topic, partition, consumer_group), db_connection_pool_active, db_connection_pool_idle, redis_cache_hit_rate, redis_cache_miss_rate. Counters: http_requests_total, kafka_messages_produced_total, kafka_messages_consumed_total, dlq_messages_total. Per-tenant dimension on all counters for noisy-neighbor detection.
  2. Grafana dashboards: (a) Platform Overview: request rate, error rate, p50/p95/p99 latency, active tenants. (b) Kafka Health: consumer lag per topic with alert thresholds, produce/consume rate, DLQ depth. (c) Database: connection pool, query latency, replication lag, partition health. (d) Per-Module: request latency + error rate per module prefix. (e) Per-Tenant: request count + latency + error rate per school_id for noisy-neighbor identification.
  3. Alert rules in Prometheus: p95 API latency > 500ms (WARNING), > 1s (CRITICAL). Error rate > 1% (WARNING), > 5% (CRITICAL). Kafka consumer lag > 1,000 any partition (WARNING), > 2,000 sustained 2 min (PAGE). DLQ messages older than 15 min (PAGE). DB replication lag > 5s (WARNING), > 30s (CRITICAL).
Produces → /metrics endpoint, 5 Grafana dashboards, Prometheus alert rules.
04Load Testing + Query Optimisation
Ops

Load test every critical hot path to establish p50/p95/p99 baselines, then use pg_stat_statements to find and fix the slowest queries.

12 Critical Hot Paths
  1. POS allergen cross-check (Cycle 20): POST /food-service/transactions with allergen resolution. Target: <50ms p95.
  2. Library catalogue GIN search (Cycle 12): GET /library/catalogue?q=... with available copies. Target: <100ms p95.
  3. Inbox query (Cycle 14): GET /messages/inbox with msg_thread_stats join. Target: <200ms p95.
  4. IAM permission check (Cycle 0): iam_effective_access_cache lookup. Target: <10ms p95.
  5. Attendance submission (Cycle 1): POST /attendance with class roster validation. Target: <100ms p95.
  6. GL batch posting (Cycle 26): POST /finance/journal-batches/:id/post with validate_batch_balance. Target: <200ms p95.
  7. QR bus pass scan (Cycle 19): POST /transport/ridership/scan. Target: <50ms p95.
  8. Student profile load (Cycle 1): GET /students/:id with accommodations + health + grades. Target: <300ms p95.
  9. Timetable render (Cycle 5): GET /scheduling/timetable/:classId. Target: <150ms p95.
  10. At-risk evaluation (Cycle 29): rpt_student_academic_summary scan. Target: <5s for 500 students.
  11. Emergency alert fan-out (Cycle 14): POST /alerts/emergency with multi-channel delivery. Target: <2s to initiate (fan-out is async).
  12. Space booking conflict check (Cycle 21): EXCLUDE gist query. Target: <20ms p95.
Query Optimisation
  1. Enable pg_stat_statements on the read replica. Collect 7 days of production-like load data.
  2. Extract top 10 slowest queries by total_exec_time. For each: EXPLAIN ANALYZE, identify missing indexes or suboptimal plans, apply targeted index additions or query rewrites.
  3. Re-run load tests to verify improvements. Document before/after p95 per hot path.
Produces → k6 load test scripts for 12 hot paths, p50/p95/p99 baseline document, top-10 query optimisation with before/after proof.
05Partition Activation
Ops

Convert partition-ready tables from simple (non-partitioned) to actual partitioned tables. These tables shipped with partition-ready schemas — queries and indexes were designed for partitioning from day one, so this is a transparent infrastructure change with no application-layer modifications.

Partition Conversions
  1. msg_threads: HASH partitioning, 64 buckets (ADR-047). Online migration via pg_partman. No query changes — all queries include thread_id in WHERE clause.
  2. msg_messages: RANGE partitioning by created_at, monthly. pg_partman auto-creates future partitions. Retention: 3 years T1.
  3. msg_moderation_log: RANGE by created_at, monthly.
  4. trn_ridership_records: RANGE by scanned_at, monthly.
  5. fds_meal_transactions: RANGE by served_at, monthly.
  6. fds_temperature_logs: RANGE by logged_at, monthly.
  7. tech_credential_access_log: RANGE by accessed_at, monthly.
  8. audit_log: RANGE by created_at, monthly. T1 12 months → T2 7 years → T3 S3 Parquet (FERPA).
  9. rpt_daily_attendance_summary: RANGE by created_at, monthly, 3-year retention.
  10. rpt_student_academic_summary: RANGE by created_at, monthly, 3-year retention.
Produces → 10 tables converted to partitioned. pg_partman configured for auto-partition creation + retention drop.
06PgBouncer + Redis Caching
Ops

Connection pooling tuned for schema-per-tenant + Redis caching for the hottest read paths with explicit invalidation contracts.

Deliverables
  1. PgBouncer configuration: Transaction-level pooling. On connection checkout: SET search_path TO tenant_{school_id}, public; via the server_reset_query hook. Pool size: 20 connections per backend (tuned per instance size). Separate pool for the platform schema read replica. Connection limits per tenant to prevent noisy-neighbor exhaustion.
  2. Redis caching layer: (a) IAM effective access cache: key iam:access:{user_id}, TTL 5 min, invalidated by iam.role_assignment.changed Kafka event + Redis Pub/Sub for immediate suspension (ADR-009 500ms primary-sticky window). (b) Unread message counts: key msg:unread:{user_id}, TTL 30 sec, invalidated on message read. (c) Catalogue available copies: key lib:avail:{item_id}, TTL 60 sec, invalidated on checkout/return. (d) Delivery gap summary: key cur:gaps:{map_id}, TTL 1 hour, invalidated on nightly worker run.
  3. Cache invalidation contracts: Every cached read path documents: (a) which Kafka event invalidates it, (b) the TTL as a worst-case staleness bound, (c) the warm-up strategy on cache miss. No cache without a documented invalidation path.
Produces → PgBouncer schema-per-tenant config, 4 Redis cache layers with documented invalidation contracts.
07DLQ Dashboard + Consumer Hardening
Ops

Wire the Dead Letter Queue dashboard (Phase 2 punch list item #1 — carried since Cycle 9), enforce envelope validation on all consumers, and implement circuit breakers on external dependencies.

Deliverables
  1. DLQ dashboard: Admin UI at /admin/dlq. Lists all dead-letter messages across all consumers: topic, partition, offset, error message, retry count, age, original event payload (redacted PII). Per-message actions: Replay (re-enqueue to original topic), Discard (acknowledge), Inspect (view full event with trace_id link to Jaeger). Alert: DLQ messages older than 15 min trigger PAGE.
  2. Consumer envelope validation: Every Kafka consumer validates the ADR-057 envelope before processing: (a) event_id present and UUID, (b) event_type matches expected, (c) tenant_id present and resolves to a provisioned tenant, (d) correlation_id present. Validation failure → DLQ with ENVELOPE_INVALID error code. Retrofit across all 17+ consumers.
  3. Circuit breakers: Every worker/consumer that calls an external dependency (PostgreSQL, Redis, AI Gateway, push provider, Stripe) implements: CLOSED (normal), OPEN (dependency failing — fail fast, do not retry), HALF-OPEN (probe recovery). Circuit state emitted as a Prometheus gauge. SAFETY_CRITICAL workers (Emergency Alert, Transport Dispatch) use read-only local cache in OPEN state.
  4. Transactional outbox evaluation: Assess replacing direct Kafka emit with the outbox pattern for guaranteed exactly-once delivery (Phase 2 punch list item #3). Decision: implement or document why deferred. If implementing: outbox table + polling publisher + dedup on consumer side via platform_event_consumer_idempotency.
Produces → DLQ admin dashboard with replay, envelope validation on all consumers, circuit breakers on all external dependencies.
08Error Budget SLOs + Alerting Pipeline
Ops

Define Service Level Objectives per module tier, wire the alerting pipeline to PagerDuty/Slack, and create the on-call runbook.

Deliverables
  1. SLO tiers: CRITICAL (99.9% availability, <500ms p95): POS transactions, health record access, emergency alerts, IAM auth, GL posting. STANDARD (99.5% availability, <1s p95): messaging, attendance, scheduling, library, store. BACKGROUND (99.0% availability, <30s p95): analytics workers, report generation, nightly materialisation.
  2. Error budget tracking: Per-module error budget computed from SLO: e.g., CRITICAL at 99.9% = 43 minutes downtime/month. Grafana panel shows remaining budget per module. Budget exhaustion triggers deployment freeze until budget recovers.
  3. Alerting pipeline: Prometheus → Alertmanager → PagerDuty (P1: CRITICAL SLO breach, DLQ age > 15 min, breach 72-hour clock) + Slack (P2: WARNING thresholds, budget <50%, consumer lag sustained). Alert routing: module prefix determines the on-call rotation.
  4. On-call runbook: Per-alert-type runbook entries: what fired, what to check, how to mitigate, who to escalate to. Linked from each Grafana alert panel.
Produces → SLO definitions for 3 tiers, error budget tracking, PagerDuty/Slack alerting, on-call runbook.
09Platform Admin Dashboard
Ops

A thin super-admin UI for platform operators that surfaces tenant health, migration state, and operational status without requiring Grafana access.

Pages
  1. Tenant Health /admin/tenants — all provisioned tenants with: migration version, table count, last activity timestamp, current consumer lag, DLQ depth, error rate (last hour). Amber/rose indicators for unhealthy tenants.
  2. Consumer Status /admin/consumers — all Kafka consumers with: lag per partition, circuit breaker state, last processed timestamp, DLQ message count. Replay button for individual DLQ messages.
  3. Partition Status /admin/partitions — partitioned table health: partition count, size per partition, retention drops pending, pg_partman next maintenance window.
  4. Migration Status /admin/migrations — Flyway migration status per tenant: current version, pending migrations, failed migrations. Bulk-apply button for pending (with dry-run preview).
Produces → Platform admin dashboard: tenant health, consumer status, partition status, migration status.
10Operational Readiness Review
Test
Ops Readiness Checklist
  1. Logging: Every module emits structured JSON. CI linter passes. trace_id present on every log line in a sample 1-hour window. PII scrub verified (grep for email patterns returns zero).
  2. Tracing: Pick 5 random HTTP requests. Each traces end-to-end through service → DB → Kafka → consumer in Jaeger/X-Ray. No broken trace chains.
  3. Metrics: /metrics endpoint returns all expected histograms, gauges, and counters. Grafana dashboards load correctly. Alert rules fire on synthetic threshold breaches.
  4. Load test baselines: All 12 hot paths meet their p95 targets. Before/after query optimisation documented. No regression from partition activation.
  5. Partitions: All 10 tables converted. pg_partman auto-creates next month's partition. Retention drops verified for test partitions older than retention window.
  6. Caching: Redis cache hit rate >80% for IAM lookups under load. Cache invalidation verified: role change invalidates within 500ms. Suspension invalidates within 1s.
  7. DLQ: Dashboard shows all consumers. Intentionally poison a message. Verify it lands in DLQ within 3 retries. Replay from dashboard succeeds.
  8. Envelope validation: Send a Kafka message with missing tenant_id. Verify consumer rejects to DLQ with ENVELOPE_INVALID.
  9. Circuit breakers: Kill Redis. Verify circuit opens. Verify SAFETY_CRITICAL workers (emergency alert) fall back to local cache. Restore Redis. Verify circuit closes.
  10. SLOs + Alerts: Simulate CRITICAL SLO breach (inject 500 errors). Verify PagerDuty page fires within 60 seconds. Verify Slack WARNING for consumer lag. Verify error budget tracking decrements.
Produces → Signed operational readiness checklist. Platform is pilot-ready from an infrastructure perspective.
