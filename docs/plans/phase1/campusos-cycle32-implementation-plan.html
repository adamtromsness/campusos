Plan Overview

Cycle 32 is the second and final hardening cycle. Like Cycle 31, it adds zero new business tables. The deliverable is the infrastructure that keeps CampusOS operational when things go wrong — from a single instance failure to a full regional outage. This is the operational guarantee that a school district needs before signing a multi-year contract: "If your primary data centre goes down, we're back within 15 minutes with less than 30 seconds of data loss."

The cycle spans 4 domains: (1) database replication — RDS Global Database with cross-region read replica and automated failover, backup validation, and point-in-time recovery testing, (2) event + cache replication — Kafka MirrorMaker2 for cross-region topic replication, Redis sentinel with cross-AZ failover, (3) storage + data residency — S3 cross-region replication with region-specific bucket policies for GDPR/data residency, tenant-region affinity enforcement at the API gateway, and (4) operational readiness — the DR runbook, automated failover testing, chaos engineering programme, and quarterly tabletop exercise framework.

Architecture — Active-Passive, Not Active-Active

Per the Architecture Review Section 21.2, the first multi-region step is active-passive (warm standby in a secondary region). Active-active requires cross-region tenant routing at the API gateway, cross-region identity resolution, and a conflict resolution strategy for financial data — last-write-wins is not acceptable for GL entries. Active-active is a future consideration when single-region scale is exhausted. This cycle builds active-passive with DNS failover.

Step-by-Step Build Plan

01RDS Global Database + Cross-Region Replication
Ops

Configure AWS RDS Global Database for cross-region replication of both the platform schema and all tenant schemas, with automated failover capability.

Deliverables
  1. RDS Global Database: Primary cluster in us-east-1. Secondary cluster in us-west-2 (warm standby). Storage-level replication with typical lag <1 second, worst-case <30 seconds. Global database supports up to 5 secondary regions (only 1 deployed this cycle).
  2. Schema replication verification: All platform tables + all tenant schemas replicate automatically (Global Database replicates at the storage level, not logical). Verify: migration version on standby matches primary, table counts match, UNIQUE constraints hold on both sides.
  3. Automated failover: RDS Global Database managed failover: promote secondary to primary in <1 minute. Configure AWS-managed failover with RPO <1 second for planned failover, <30 seconds for unplanned. Application reconnection via PgBouncer + DNS update.
  4. Read replica routing: Cycle 31's read replica routing (platform_read_replica_routing, platform_read_replica_health) extended to include the cross-region standby as a read replica during normal operations. Analytics queries can optionally route to the standby to offload the primary.
Produces → RDS Global Database with <30s RPO, automated failover, cross-region read routing.
02Automated Backup Validation
Ops

Automated weekly validation that backups are restorable and data-intact. A backup you can't restore is not a backup.

Deliverables
  1. Weekly snapshot restore job: GitHub Actions workflow (Sunday 04:00 UTC): restore the latest automated RDS snapshot to a temporary instance, run Flyway validation (migration version matches primary), run table count check per schema (within ±1% of primary), run row count spot-checks on 10 critical tables (sis_students, iam_person, fin_gl_entries, audit_log, msg_messages, pay_ledger_entries, trn_ridership_records, fds_meal_transactions, pfl_portfolios, dpo_data_breach_records), tear down the temporary instance. Alert on any failure.
  2. Point-in-time recovery (PITR) test: Monthly: restore to a specific timestamp (15 minutes ago), verify data consistency at that point, document recovery time. Target: PITR complete within 30 minutes for the full database.
  3. Cross-region backup replication: RDS automated snapshot copy to us-west-2. Retention: 35 days in primary, 7 days in secondary. Verified: secondary snapshots are independently restorable (test quarterly).
  4. Backup monitoring: Prometheus metric: backup_validation_last_success_timestamp. Alert if more than 8 days since last successful validation.
Produces → Weekly automated backup validation, monthly PITR test, cross-region snapshot copy, backup monitoring alert.
03Kafka MirrorMaker2 + Event Replication
Ops

Replicate the Kafka event stream to the standby region so consumers in the standby can resume from the correct offset after failover.

Deliverables
  1. MirrorMaker2 configuration: Replicate all operational topics from primary MSK cluster (us-east-1) to standby MSK cluster (us-west-2). Topic naming: source topic dev.pay.payment.received becomes us-east-1.dev.pay.payment.received in the standby cluster. Consumer group offset sync enabled.
  2. Consumer offset translation: MM2 translates consumer group offsets from primary to standby. On failover: consumers in us-west-2 resume from the translated offset, not from earliest. Verified: simulate failover, confirm consumers process only events after the last committed offset in primary.
  3. Idempotency record replication: platform_event_consumer_idempotency replicates via Global Database. On failover: consumers that reprocess events near the boundary will find the idempotency key and skip duplicates. No double-processing of financial events.
  4. DLQ replication: DLQ topics replicate. DLQ dashboard in standby shows replicated dead letters. Replay in standby routes to standby consumers.
  5. Replication lag monitoring: MM2 checkpoint lag metric exported to Prometheus. Alert if replication lag exceeds 5 minutes sustained.
Produces → Cross-region Kafka replication with offset translation, idempotency dedup, DLQ sync, lag monitoring.
04Redis Sentinel + Cache Failover
Ops

Redis cross-region replication for the IAM cache and tenant routing cache, with documented cold-start rebuild strategy for the standby region.

Deliverables
  1. ElastiCache Global Datastore: Primary Redis cluster in us-east-1, read replica in us-west-2. IAM effective access cache + tenant routing cache replicate automatically. Typical lag <1 second.
  2. Cross-AZ failover: Within us-east-1: Multi-AZ with automatic failover. ElastiCache promotes replica on primary failure. Application reconnects via the primary endpoint (unchanged).
  3. Cold-start rebuild strategy: If Redis is completely lost in the standby region (no replication data): IAM cache rebuilt from iam_role_assignment → roles → role_permissions. Tenant routing rebuilt from platform_tenant_routing. Cycle 31's caching layer (unread counts, catalogue copies, gap summaries) rebuilds on first cache miss. Documented warm-up time: ~5 minutes for a 500-student school.
  4. Suspension propagation: Account suspension (iam.account.suspended) propagates via Redis Pub/Sub within the primary region (<1s). Cross-region: the Global Datastore replicates the SUSPENDED_ACCOUNTS set. On failover: the standby has the suspension list. Verified: suspend an account in primary, verify suspension effective in standby within 5 seconds.
Produces → ElastiCache Global Datastore, cross-AZ failover, cold-start rebuild strategy, suspension propagation verification.
05S3 Cross-Region Replication + Data Residency
Ops

Cross-region replication for all S3 buckets with GDPR data residency enforcement for EU/UK tenants.

Deliverables
  1. S3 CRR (Cross-Region Replication): All S3 buckets in us-east-1 replicate to us-west-2. Includes: lesson videos, uploaded documents, paystub PDFs, profile images, credential vault documents, DPA documents, privacy notice documents, report outputs, export files.
  2. EU/UK data residency: EU/UK tenants get dedicated S3 buckets in eu-west-2 (London). Replication stays within EU: eu-west-2 ↔ eu-west-1 (Ireland), never to us-east-1. Bucket policy denies PutObject from non-EU principals. Verified: upload a document as an EU tenant, confirm it lands in eu-west-2, confirm it does NOT replicate to us-east-1.
  3. CloudFront PII restriction: CloudFront distribution configured with geo-restriction for PII-bearing content: EU tenant content served only from EU edge locations. Static assets (JS, CSS, public images) cached globally. Signed URLs for all PII content with 1-hour expiry.
  4. S3 versioning + lifecycle: Versioning enabled on all buckets (deletion protection). Lifecycle: current versions retained indefinitely, non-current versions expired after 90 days, incomplete multipart uploads aborted after 7 days.
Produces → S3 CRR for all buckets, EU data residency pinning, CloudFront PII restrictions, versioning + lifecycle.
06Tenant-Region Affinity + API Gateway Routing
Code

Enforce tenant-region affinity at the API gateway so a tenant's requests always route to their home region's infrastructure.

Deliverables
  1. home_region enforcement: platform_tenant_routing.home_region (added in Cycle 0, defaulted to primary region) now actively enforced. TenantRoutingDataSource (ADR-042) reads home_region from Redis cache and selects the regional DB endpoint. A US tenant in us-east-1 never touches the eu-west-2 database.
  2. API gateway region routing: Route 53 latency-based routing + API Gateway regional endpoints. EU tenants resolve to the EU API Gateway endpoint. US tenants resolve to the US endpoint. The gateway validates that the resolved region matches platform_tenant_routing.home_region. Mismatch returns 421 Misdirected Request.
  3. DPO regional workflow routing: dpo_subject_access_requests and dpo_erasure_requests processed in the tenant's home_region. The DPO Governance API (Cycle 30) validates that the executing worker is in the correct region before processing. Cross-region DPO operations documented in dpo_data_processing_agreements.
  4. Tenant region migration procedure: Documented procedure for moving a tenant from one region to another (e.g., US school opens a UK campus). Steps: provision tenant schema in target region, replicate data via pg_dump/pg_restore, update platform_tenant_routing.home_region, verify, cut over DNS, decommission source schema. Estimated downtime: <30 minutes per tenant.
Produces → home_region enforcement at gateway, regional DPO routing, tenant migration procedure.
07DR Runbook + Communication Templates
Ops

The disaster recovery runbook that the on-call team follows when infrastructure fails.

6 Failure Scenarios
  1. Scenario 1 — Single instance failure: ECS task dies. Auto-replaced by ECS service scheduler. No manual action. Verify health check + auto-replacement within 2 minutes.
  2. Scenario 2 — Availability Zone failure: One AZ in us-east-1 goes down. Multi-AZ RDS fails over automatically (<30s). ECS tasks redistribute to healthy AZs. ElastiCache sentinel promotes replica. Verify all services operational within 5 minutes. No manual action required.
  3. Scenario 3 — Primary database failure: RDS primary instance unresponsive. Global Database promotes standby. PgBouncer reconnects to new primary endpoint. Kafka consumers pause and resume. Verify: <5 minute RTO, <1 second RPO. On-call validates data integrity post-failover.
  4. Scenario 4 — Full regional failure: us-east-1 completely unavailable. Route 53 health check fails 3× → DNS failover to us-west-2. Global Database promotes us-west-2 to primary. Kafka consumers in us-west-2 resume from translated offsets. Redis cold-start rebuild (~5 min). S3 serves from replicated buckets. Verify: <15 minute RTO, <30 second RPO. Communication template: notify all school admins via emergency SMS (pre-cached phone numbers in standby).
  5. Scenario 5 — Kafka cluster failure: MSK cluster unresponsive. Producers buffer in-memory (30s). MSK auto-recovers brokers. Consumer offsets recovered from coordination topic. If full cluster loss: consumers replay from earliest available offset, idempotency records prevent duplicates. Verify: <10 minute recovery.
  6. Scenario 6 — Data corruption: Logical data corruption detected (bad migration, application bug). Immediate: isolate affected tenants (feature flag kill-switch). PITR: restore from point-in-time before corruption. Selective restore: pg_dump affected schemas from PITR instance, pg_restore into production. Verify: data integrity checks on restored schemas. Communication: notify affected schools with timeline.
Communication Templates
  1. Incident notification (to schools): "CampusOS is experiencing a service disruption. Our team is actively working to restore service. We expect resolution within [ETA]. Your data is safe. We will update you every 30 minutes."
  2. Resolution notification: "Service has been fully restored as of [time]. No data was lost. A detailed incident report will be shared within 48 hours."
  3. Post-incident report template: Timeline, root cause, impact (tenants affected, duration), remediation actions, preventive measures, follow-up items.
Produces → 6-scenario DR runbook, escalation matrix, 3 communication templates, post-incident review framework.
08Automated Failover Testing
Test

Monthly automated failover exercises that prove the DR infrastructure works without waiting for a real incident.

Deliverables
  1. Monthly synthetic failover: Automated workflow (first Sunday of each month, 02:00 UTC staging): trigger RDS Global Database failover from primary to standby. Verify: application reconnects within target RTO (<15 min). Kafka consumers resume from correct offsets. Redis cache available (replicated or rebuilt). S3 objects accessible from standby region. Run smoke test suite against standby. Fail back to primary after verification.
  2. Consumer resume verification: During failover: verify each of the 17+ consumers resumes from the last committed offset. No events skipped. No events double-processed (idempotency check). GL consumer specifically verified: no duplicate financial postings.
  3. Cache rebuild verification: Kill Redis in standby before failover. Verify: IAM cache rebuilds from DB within 5 minutes. Tenant routing resolves correctly. First request for each user experiences cache-miss latency (~200ms), subsequent requests hit cache (<10ms).
  4. Failover metrics: Record per failover exercise: actual RTO (minutes), actual RPO (seconds of data lag), consumer resume lag (seconds), cache rebuild time (seconds), total smoke test pass rate. Trend over time in Grafana.
Produces → Monthly automated failover exercise, consumer/cache verification, failover metrics tracking.
09Chaos Engineering Programme
Test

Proactive failure injection in staging to find weaknesses before they find you in production.

Experiments
  1. Instance kills (Chaos Monkey): Randomly terminate ECS tasks in staging during business hours. Verify: ECS service scheduler replaces within 2 minutes. No user-visible errors (load balancer health check routes around). Metric: mean time to replacement.
  2. AZ failure simulation: Block all network traffic to one AZ in staging. Verify: Multi-AZ RDS fails over. ECS tasks redistribute. No user-visible downtime beyond ~30s. Metric: failover duration.
  3. Network partition injection: Introduce 5-second network latency between application and database. Verify: circuit breakers open. Requests fail fast (not hang). Health check reports degraded. When partition heals: circuit closes. Requests resume. No data corruption.
  4. DB failover drill: Force RDS failover in staging. Verify: PgBouncer reconnects. Consumers pause and resume. No orphaned transactions. Metric: application recovery time.
  5. Kafka broker kill: Terminate one MSK broker. Verify: producers and consumers continue with remaining brokers. Replication factor ensures no data loss. MSK auto-replaces the broker. Metric: producer/consumer impact duration.
  6. Redis eviction pressure: Fill Redis to 90% capacity in staging. Verify: eviction policy (volatile-lru) evicts correct keys. IAM cache misses fall back to DB. No application errors. Metric: cache hit rate under pressure.
Produces → 6 chaos experiments with documented results, weakness identification, remediation tracking.

Test

The final review that certifies the platform is disaster-ready, plus the framework for ongoing quarterly exercises.

DR Readiness Checklist
  1. Database: Global Database replicating with <30s lag. Weekly backup validation passing. Monthly PITR test successful. Cross-region snapshots verified restorable.
  2. Kafka: MirrorMaker2 replicating all topics with <5 min lag. Consumer offset translation verified. Idempotency records replicating. DLQ sync confirmed.
  3. Redis: Global Datastore replicating IAM + routing caches. Cold-start rebuild tested and documented. Suspension propagation verified cross-region.
  4. S3: CRR active for all buckets. EU data residency verified (no leakage to US). CloudFront PII restrictions active. Versioning enabled.
  5. Tenant routing: home_region enforced at API gateway. Regional DPO routing verified. Tenant migration procedure documented and tested.
  6. Runbook: All 6 scenarios documented. Communication templates reviewed by school relations team. Escalation matrix current.
  7. Failover testing: At least 2 successful monthly failover exercises completed. RTO <15 min achieved. RPO <30s achieved. Consumer resume verified. Cache rebuild verified.
  8. Chaos engineering: All 6 experiments completed in staging. Weaknesses identified and remediated. No critical findings outstanding.
Quarterly Tabletop Exercise Framework
  1. Format: 2-hour facilitated exercise with the full engineering + ops team. One scenario presented (rotating quarterly through the 6 runbook scenarios + novel scenarios). Team walks through the runbook steps, identifies gaps, makes decisions, logs actions.
  2. Deliverable per exercise: Decision log (who decided what, when), gap identification (runbook steps that were unclear or incomplete), action items (remediation with owners + deadlines), updated runbook (incorporate lessons learned).
  3. First exercise: Conducted as part of Cycle 32. Scenario: "It's Tuesday 10:30 AM. us-east-1 reports a major outage affecting all services. 200 schools are in the middle of morning attendance. The Emergency Alert service was processing a lockdown drill when the outage began. Walk through the response."
Produces → Signed DR readiness checklist. First quarterly tabletop exercise completed. Core roadmap complete. CampusOS is pilot-ready.
