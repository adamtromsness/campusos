Cycle 11.1: Wellbeing
Check-Ins

Student-facing pulse surveys with counsellor-deployed targeting, multi-question-type responses, automatic flagging for follow-up, and a 5-type alert system with SELF_HARM_INDICATOR auto-escalation to administrators. The first student-input surface in the platform.
May 2026 · 8 Steps · ERD v11 · M27 Domain 5 (6 tables) · COU-004

Plan Overview

Cycle 11.1 ships the 6 wellbeing tables deferred from Cycle 11. This is a self-contained sub-system with its own student-facing surface — the first time a student directly inputs data into CampusOS. The counsellor creates a survey template with questions across 5 domains (Academic, Social, Emotional, Physical, Safety), deploys it to a target audience (caseload, class, year group, school-wide, or custom list), and the platform generates individual check-in rows for each targeted student. Students complete check-ins via a dedicated student UI. Application logic flags concerning responses and generates alerts with a 5-type enum (FEELS_UNSAFE, WANTS_TO_TALK, SIGNIFICANT_SCORE_DROP, PERSISTENT_LOW_SCORE, SELF_HARM_INDICATOR). SELF_HARM_INDICATOR alerts auto-escalate to the school administrator.

The data sensitivity model differs from Cycle 11's FERPA notes: wellbeing responses are student-generated self-report data visible to the counselling team and school administration. Students may view their own responses. Teachers see only aggregated trends (no individual responses) per the COU-004 function library. Parents do not see wellbeing data.

Safety — SELF_HARM_INDICATOR Auto-Escalation

When a student's response matches the SELF_HARM_INDICATOR trigger criteria (configurable per template — e.g., SAFETY domain score ≤ 1 on a 1–5 scale, or YES on "Do you feel like hurting yourself?"), the system automatically creates an alert row with alert_type=SELF_HARM_INDICATOR and emits svc.wellbeing.alert.created. This Kafka event should be consumed by the Cycle 3 NotificationConsumer (future wiring) to send an immediate IN_APP + EMAIL notification to the school administrator AND the assigned counsellor. The alert auto-escalation is not configurable by the school — it fires unconditionally whenever the trigger criteria match.

Vertical Slice Deliverable

Counsellor creates a "Weekly Emotional Check-In" template with 5 questions across Emotional + Safety domains (3 SCALE_1_5, 1 YES_NO "Do you want to talk to someone?", 1 EMOJI_SCALE) → deploys to Maya's caseload targeting → platform generates a PENDING check-in for Maya → Maya opens the student wellbeing page, sees the pending check-in, and submits responses (Safety score=2, "Do you want to talk?"=YES) → application logic flags the check-in for follow-up and creates a WANTS_TO_TALK alert → counsellor sees the alert in the alert queue, acknowledges it, and documents follow-up → admin views the school-wide wellbeing dashboard showing aggregated domain scores and alert counts → Maya sees her own responses on the student portal → teacher sees only "1 check-in completed this week" aggregated trend — no individual responses.

What's In / What's Deferred

In scope (6 tables): svc_wellbeing_survey_templates, svc_wellbeing_questions, svc_wellbeing_deployments, svc_wellbeing_checkins, svc_wellbeing_responses, svc_wellbeing_alerts. COU-004 function (read + write + admin tiers).

Deferred: Response RANGE-partitioning by month (tagged in ERD — ships as a simple table now; partitioning is a Phase 3 ops concern when data volume warrants it). Scheduled deployment auto-activation (manual activation this cycle; a cron/worker that flips SCHEDULED → ACTIVE at deploy_at is a future enhancement). Score-drop detection across deployments (SIGNIFICANT_SCORE_DROP and PERSISTENT_LOW_SCORE alerts require historical comparison — this cycle implements FEELS_UNSAFE, WANTS_TO_TALK, and SELF_HARM_INDICATOR which can fire on single-response evaluation). Cycle 3 NotificationConsumer wiring for svc.wellbeing.alert.created (emit lands on Kafka; no consumer yet).

Step-by-Step Build Plan

01 Wellbeing Survey Schema — Templates + Questions + Deployments
Schema

The counsellor-authored survey infrastructure: reusable templates with ordered questions across 5 wellbeing domains, and the deployment mechanism that targets student audiences.

Tables (3)
  1. svc_wellbeing_survey_templates — school_id UUID, name TEXT NOT NULL, description TEXT, frequency_recommendation TEXT NOT NULL 4-value CHECK (DAILY, WEEKLY, MONTHLY, AS_NEEDED), is_active BOOLEAN DEFAULT true, created_by UUID FK(hr_employees) NOT NULL. UNIQUE(school_id, name). INDEX(school_id, is_active). The template is the reusable survey definition; each deployment creates a fresh batch of check-ins from it.
  2. svc_wellbeing_questions — template_id UUID FK NOT NULL, question_text TEXT NOT NULL, question_type TEXT NOT NULL 5-value CHECK (SCALE_1_5, SCALE_1_10, YES_NO, FREE_TEXT, EMOJI_SCALE), domain TEXT NOT NULL 5-value CHECK (ACADEMIC, SOCIAL, EMOTIONAL, PHYSICAL, SAFETY), sort_order INT NOT NULL. INDEX(template_id, sort_order). The SAFETY domain questions are the trigger surface for SELF_HARM_INDICATOR and FEELS_UNSAFE alerts.
  3. svc_wellbeing_deployments — school_id UUID, template_id UUID FK(svc_wellbeing_survey_templates) NOT NULL, deployed_by UUID FK(hr_employees) NOT NULL, deploy_at TIMESTAMPTZ NOT NULL, expires_at TIMESTAMPTZ nullable, target_type TEXT NOT NULL 5-value CHECK (CASELOAD, CLASS, YEAR_GROUP, SCHOOL, CUSTOM_LIST), target_ids UUID[] nullable (null for CASELOAD which auto-targets the deploying counsellor's active caseload; class IDs, year group IDs, or specific student IDs otherwise), status TEXT NOT NULL DEFAULT 'SCHEDULED' 4-value CHECK (SCHEDULED, ACTIVE, COMPLETED, CANCELLED), total_targeted INT nullable, total_completed INT nullable. INDEX(school_id, status). On SCHEDULED → ACTIVE: Step 4 service generates svc_wellbeing_checkins rows for all targeted students.
Produces → 3 new tables. Migration: 039_svc_wellbeing_templates.sql.
02 Check-In + Responses + Alerts Schema
Schema

The student-facing check-in instances, per-question responses, and the alert system that flags concerning answers for counsellor triage.

Tables (3)
  1. svc_wellbeing_checkins — One row per student per deployment (or ad-hoc). school_id UUID, student_id UUID FK(sis_students) NOT NULL, template_id UUID FK(svc_wellbeing_survey_templates) NOT NULL, deployment_id UUID FK(svc_wellbeing_deployments) nullable (null for ad-hoc check-ins), completed_at TIMESTAMPTZ nullable (null = not yet completed; the student UI renders these as PENDING), flagged_for_follow_up BOOLEAN DEFAULT false (set by application logic in Step 5 when responses indicate concern), assigned_counselor_id UUID FK(hr_employees) nullable. INDEX(student_id, completed_at DESC). Partial INDEX(flagged_for_follow_up, completed_at) WHERE flagged_for_follow_up=true — the counsellor follow-up queue. Partial INDEX(deployment_id, completed_at) WHERE deployment_id IS NOT NULL.
  2. svc_wellbeing_responses — Per-question response within a check-in. checkin_id UUID FK NOT NULL, question_id UUID FK(svc_wellbeing_questions) NOT NULL, numeric_response SMALLINT nullable (SCALE_1_5, SCALE_1_10, EMOJI_SCALE map to numeric; YES_NO maps to 1/0), text_response TEXT nullable (FREE_TEXT answers). UNIQUE(checkin_id, question_id) — one response per question per check-in. Student-generated self-report data. Access restricted to counselling team + admin. Students may view own responses only.
  3. svc_wellbeing_alerts — student_id UUID FK(sis_students) NOT NULL, response_id UUID FK(svc_wellbeing_responses) NOT NULL (the specific response that triggered the alert), alert_type TEXT NOT NULL 5-value CHECK (FEELS_UNSAFE, WANTS_TO_TALK, SIGNIFICANT_SCORE_DROP, PERSISTENT_LOW_SCORE, SELF_HARM_INDICATOR), status TEXT NOT NULL DEFAULT 'NEW' 4-value CHECK (NEW, ACKNOWLEDGED, IN_PROGRESS, RESOLVED), acknowledged_by UUID FK(hr_employees) nullable, acknowledged_at TIMESTAMPTZ nullable, resolution_notes TEXT nullable. INDEX(student_id, status). Partial INDEX(status) WHERE status IN ('NEW','ACKNOWLEDGED','IN_PROGRESS') — the open-alerts queue. SELF_HARM_INDICATOR auto-escalates to administrator via Kafka emit.
Produces → 3 new tables. Migration: 040_svc_wellbeing_checkins.sql. Total Cycle 11.1 tables: 6.

04 Survey Template + Deployment NestJS Module
Code
Services & Endpoints
  1. SurveyTemplateService — GET /counselling/wellbeing/templates (counsellor + admin: active templates for the school), GET /counselling/wellbeing/templates/:id (with inlined questions ordered by sort_order), POST /counselling/wellbeing/templates (admin or counsellor; creates template + questions in one tx), PATCH /counselling/wellbeing/templates/:id (update name, description, frequency, is_active; deactivate rather than delete so historical deployments retain their FK), POST /counselling/wellbeing/templates/:id/questions (add question), PATCH /counselling/wellbeing/questions/:id (update question text, type, domain, sort_order), DELETE /counselling/wellbeing/questions/:id (only when no responses reference it yet).
  2. DeploymentService — GET /counselling/wellbeing/deployments (counsellor: own; admin: all; filters on status, template), GET /counselling/wellbeing/deployments/:id (with inlined completion stats: total_targeted, total_completed, completion_rate), POST /counselling/wellbeing/deployments (counsellor or admin; validates target_type constraints; stamps deployed_by from actor.employeeId), PATCH /counselling/wellbeing/deployments/:id/activate (SCHEDULED → ACTIVE; resolves target audience into student IDs and bulk-INSERTs svc_wellbeing_checkins rows with completed_at=null; stamps total_targeted; assigns counsellor from deployer's caseload ownership where applicable), PATCH /counselling/wellbeing/deployments/:id/complete (ACTIVE → COMPLETED), PATCH /counselling/wellbeing/deployments/:id/cancel (any non-terminal → CANCELLED).
Produces → WellbeingModule with 2 services, ~13 endpoints. The activate endpoint is the keystone — it resolves the target audience and bulk-generates check-in rows.
05 Check-In + Response + Alert NestJS Module
Code
Services & Endpoints
  1. CheckInService — GET /counselling/wellbeing/checkins (counsellor: for caseload students; admin: school-wide; student: own only; filters on completed/pending, flagged, deployment), GET /counselling/wellbeing/checkins/:id (with inlined responses; student sees own; counsellor sees caseload; admin sees all), POST /counselling/wellbeing/checkins/:id/submit (STUDENT-FACING keystone. Accepts an array of {questionId, numericResponse?, textResponse?}. Validates every question in the template has a response. Bulk-INSERTs svc_wellbeing_responses inside one tx. Stamps completed_at=now(). Runs the flag + alert evaluation logic — see below. Updates the deployment's total_completed counter).
  2. Alert evaluation logic (inside the submit tx): after responses are persisted, the service scans for trigger conditions: (a) WANTS_TO_TALK — any YES_NO question with numeric_response=1 (YES) in the SAFETY or EMOTIONAL domain, (b) FEELS_UNSAFE — any SAFETY-domain SCALE question with numeric_response ≤ 1 (lowest rating), (c) SELF_HARM_INDICATOR — any SAFETY-domain question with text matching a configurable keyword list OR numeric_response=1 on a specifically-tagged question (the template author tags a question as a self-harm indicator via a future is_safety_critical flag — for this cycle, the trigger fires on SAFETY+SCALE_1_5 ≤ 1). When a trigger matches: flag the check-in (flagged_for_follow_up=true), create a svc_wellbeing_alerts row with the matching response_id, and emit svc.wellbeing.alert.created on Kafka. SELF_HARM_INDICATOR additionally auto-escalates by emitting with autoEscalate=true in the payload.
  3. AlertService — GET /counselling/wellbeing/alerts (counsellor: own caseload students; admin: school-wide; filters on status, alert_type), PATCH /counselling/wellbeing/alerts/:id/acknowledge (NEW → ACKNOWLEDGED; stamps acknowledged_by + acknowledged_at), PATCH /counselling/wellbeing/alerts/:id/resolve (any open state → RESOLVED with resolution_notes). Teachers see alert counts only (no student-level detail). Students and parents never see alerts.
Produces → 2 services, ~8 endpoints, 1 Kafka emit (svc.wellbeing.alert.created). Total Cycle 11.1 endpoints: ~21.
06 Counsellor Wellbeing UI — Templates + Deployments + Alerts
UI
Pages
  1. Wellbeing Dashboard /counselling/wellbeing — extends the existing Counselling app tile. Three panels: (1) Active deployments with completion progress bars (total_completed / total_targeted), (2) Open alerts queue (NEW + ACKNOWLEDGED, sorted by alert_type severity: SELF_HARM_INDICATOR first, then FEELS_UNSAFE, then WANTS_TO_TALK), (3) Recent completed check-ins with flagged/unflagged pills.
  2. Template Builder /counselling/wellbeing/templates/:id — template header (name, description, frequency). Draggable question list with type pill + domain pill per row. Add-question form with type dropdown, domain dropdown, question text. Question edit inline. Delete question (blocked when responses exist).
  3. Deployment Manager /counselling/wellbeing/deployments/:id — deployment card with target_type pill + status pill + deploy/expire dates + completion stats. Student check-in list with completed/pending status per row. Activate / Complete / Cancel buttons per status. For completed check-ins: click to see per-student responses (counsellor detail view).
  4. Alert Queue /counselling/wellbeing/alerts — filter chips: New / Acknowledged / In progress / Resolved / All. Per-row: student name, alert_type pill (rose gradient: SELF_HARM_INDICATOR deepest red), linked response preview, status pill. Acknowledge + resolve buttons. Resolution notes modal.
Produces → Wellbeing dashboard, template builder, deployment detail, alert queue. Extends the /counselling route family.
07 Student Wellbeing UI — Check-In Completion
UI
Pages
  1. Student Check-In Page /wellbeing — The first student-input surface in CampusOS. New "Wellbeing" tile on the student launchpad gated on COU-004:read (granted to students in the Step 3 seed). Lists pending check-ins (completed_at IS NULL) with template name + counsellor name + due info. "Start check-in" button opens the completion flow.
  2. Check-In Completion Flow /wellbeing/checkins/:id — question-by-question card layout with appropriate input per question_type: SCALE_1_5 renders 5 radio buttons (1 = "Not at all" to 5 = "Very much"); SCALE_1_10 renders a slider; YES_NO renders two large toggle buttons; FREE_TEXT renders a textarea (500 char limit); EMOJI_SCALE renders 5 emoji faces (maps to 1–5 numeric). Submit button validates all questions answered. On submit: POST /checkins/:id/submit with the full response array. Success confirmation shows "Thank you for checking in" with a warm illustration.
  3. My Responses /wellbeing/history — student sees their own completed check-ins (newest first) with date + template name. Click to see own responses (read-only). Students do NOT see their alert status (they do not know they were flagged — the counsellor initiates any follow-up conversation naturally).
Produces → Student wellbeing tile + check-in completion flow + response history. The first student-input surface in the platform.
