P2-1: Visitor Management

Lobby kiosk sign-in with encrypted PII and HMAC blind-index returning-visitor lookup, configurable visitor types with per-type safeguarding check requirements, banned persons screening with real-time kiosk blocking (ADR-015: registry data transient, never persisted), staff-initiated pre-registration with QR-code expedited sign-in, recurring visitor schedules for regular contractors, emergency muster snapshots with per-visitor accountability tracking, and volunteer sign-in via platform_volunteer_profiles. The first surface a school visitor touches.
May 2026 · 10 Steps · ERD v11 · M90 Visitor Management (9 tables — all in scope) · ADR-015/032 · SAF-001 · Phase 2 Cycle 1

Plan Overview

Phase 2 Cycle 1 builds the M90 Visitor Management module — all 9 ERD tables. This is the first module a school visitor interacts with and the first Phase 2 cycle. Every person who enters the building — parents, contractors, vendors, volunteers, guest speakers, prospective families — signs in through this system. The reception kiosk is the school's front door.

The module has two security keystones. First, PII encryption: vis_visitors.email_encrypted and phone_encrypted store AES-256 encrypted values; email_hash and phone_hash are HMAC blind indexes enabling equality lookup without decryption (same pattern as the Cycle 22 credential vault but for visitor PII). Second, banned persons screening: on every sign-in, the kiosk computes HMAC of the visitor's name + DOB and checks against vis_banned_persons.name_hash. A match blocks sign-in and immediately alerts the safeguarding officer. Per ADR-015, third-party registry data (DBS/background check results) is transient — only the pass/fail status and reference ID are stored, never the registry content itself.

Safety — Banned Persons Screening

The vis_banned_persons table uses HMAC blind indexing (name_hash computed from normalised full name + DOB) so that the kiosk can check for bans without storing searchable plaintext names in an indexed column. On sign-in: compute HMAC of entered name + DOB → SELECT WHERE name_hash = $computed AND is_active = true. On match: BLOCK sign-in, display a neutral message ("Please see reception staff"), immediately emit vis.banned_person.detected to alert the safeguarding officer. The visitor never sees why they were blocked. The ban_type field (COURT_ORDER, RESTRAINING_ORDER, SAFEGUARDING, SCHOOL_DECISION) and supporting document S3 key are visible only to admin with safeguarding_ban:read permission.

Vertical Slice Deliverable

Admin configures 4 visitor types: "Parent" (safeguarding check not required), "Contractor" (safeguarding check required, amber badge), "Guest Speaker" (safeguarding check required, green badge), "Volunteer" (safeguarding check required, links to platform_volunteer_profiles per ADR-032) → admin adds a banned person (John Doe, COURT_ORDER, court order document uploaded) → teacher Rivera pre-registers a guest speaker for Thursday's assembly (creates QR-code token, email sent to speaker) → Thursday morning: speaker arrives at kiosk, scans QR code → pre-registration resolved, name pre-filled, safeguarding check status = PASSED (pre-verified) → sign-in created, badge prints → a parent arrives, types name + email at kiosk → returning visitor detected via email_hash (signed in 3 weeks ago) → previous record auto-fills → sign-in created → a contractor arrives → banned person check fires against name_hash → NO MATCH → safeguarding check initiated → status = PASSED → sign-in created → later, someone matching the banned person's HMAC arrives → kiosk BLOCKS, displays neutral message, vis.banned_person.detected fires, safeguarding officer paged → fire alarm sounds → admin creates emergency muster snapshot → all currently signed-in visitors (signed_out_at IS NULL) batch-inserted into vis_muster_entries → reception staff marks each visitor as ACCOUNTED_FOR or EVACUATED → total on-site count verified against muster entries.

What's In / What's Deferred

In scope (all 9 tables): vis_visitor_types, vis_visitors, vis_sign_ins, vis_pre_registrations, vis_recurring_visitors, vis_banned_persons, vis_emergency_muster, vis_muster_entries, vis_sign_in_settings. Function SAF-001 (Visitor Management).

Deferred: Physical badge printing integration (badge design ready; hardware integration deferred). Third-party DBS/background check API integration (manual status entry this cycle). Photo capture at kiosk. NDA/agreement signing at kiosk (digital signature capture). Multi-building sign-in tracking (single building this cycle). Visitor analytics dashboard (rpt_visitor_summary deferred to Cycle 29.1).

Step-by-Step Build Plan

01Visitor Types + Visitors + Settings Schema
Schema
Tables (3)
  1. vis_visitor_types — school_id UUID, name TEXT NOT NULL, requires_safeguarding_check BOOLEAN DEFAULT true, badge_color TEXT. UNIQUE(school_id, name).
  2. vis_visitors — ENCRYPTED PII. school_id UUID, first_name TEXT NOT NULL, last_name TEXT NOT NULL, company TEXT, email_encrypted TEXT (AES-256), email_hash TEXT NOT NULL (HMAC blind index for returning-visitor lookup: SELECT WHERE email_hash = hmac($email, $secret)), phone_encrypted TEXT, phone_hash TEXT, visitor_type_id UUID FK. UNIQUE(school_id, email_hash). INDEX(email_hash) for kiosk lookup.
  3. vis_sign_in_settings — school_id UUID UNIQUE, require_photo_id BOOLEAN DEFAULT false, require_purpose BOOLEAN DEFAULT true, auto_sign_out_hours INT DEFAULT 12, safeguarding_provider TEXT nullable, badge_template TEXT DEFAULT 'STANDARD'.
Produces → 3 tables. Migration: 095_vis_visitors.sql.
02Sign-Ins + Pre-Registration + Recurring Schema
Schema
Tables (3)
  1. vis_sign_ins — school_id UUID, visitor_id UUID FK NOT NULL, signed_in_at TIMESTAMPTZ NOT NULL, signed_out_at TIMESTAMPTZ nullable, host_id UUID FK nullable (staff member being visited), purpose TEXT, building_id UUID FK(fac_buildings) nullable, safeguarding_check_status TEXT NOT NULL 4-value CHECK (PASSED, FLAGGED, BYPASSED_BY_ADMIN, NOT_REQUIRED), safeguarding_check_ref TEXT (third-party reference ID only — ADR-015: registry data transient, never persisted), bypass_admin_id UUID FK nullable, bypass_reason TEXT nullable. CHECK(safeguarding_check_status = 'BYPASSED_BY_ADMIN' IMPLIES bypass_admin_id IS NOT NULL AND bypass_reason IS NOT NULL AND length(trim(bypass_reason)) > 10). Partial INDEX(school_id, signed_in_at) WHERE signed_out_at IS NULL — emergency muster query instantaneous. BRIN on signed_in_at for historical compliance reports.
  2. vis_pre_registrations — school_id UUID, visitor_id UUID FK, expected_at TIMESTAMPTZ, purpose TEXT, host_id UUID FK, qr_code_token TEXT NOT NULL UNIQUE, expires_at TIMESTAMPTZ, used_at TIMESTAMPTZ. Partial INDEX(expires_at) WHERE used_at IS NULL. Cleanup: DELETE WHERE expires_at < now() AND used_at IS NULL.
  3. vis_recurring_visitors — school_id UUID, visitor_id UUID FK, access_schedule JSONB (days/times), valid_from DATE, valid_to DATE, approved_by UUID FK, is_active BOOLEAN DEFAULT true. GIN INDEX on access_schedule. INDEX(visitor_id, valid_from, valid_to).
Produces → 3 tables. Migration: 096_vis_sign_ins.sql.
03Banned Persons + Emergency Muster Schema
Schema
Tables (3)
  1. vis_banned_persons — SAFETY KEYSTONE. school_id UUID NOT NULL, first_name TEXT NOT NULL, last_name TEXT NOT NULL, name_hash TEXT NOT NULL (HMAC blind index: computed from normalised lowercase full name + DOB), date_of_birth DATE, photo_s3_key TEXT, ban_reason TEXT NOT NULL, ban_type TEXT NOT NULL 5-value CHECK (COURT_ORDER, SCHOOL_DECISION, SAFEGUARDING, RESTRAINING_ORDER, OTHER), ban_order_s3_key TEXT, added_by UUID FK NOT NULL, reviewed_by UUID FK, last_reviewed_at DATE, is_active BOOLEAN DEFAULT true, effective_from DATE NOT NULL, effective_to DATE (null = indefinite). INDEX(school_id, name_hash) WHERE is_active = true — kiosk real-time lookup.
  2. vis_emergency_muster — school_id UUID, incident_id UUID nullable (soft to inc_incidents when M91 is built), created_by UUID FK NOT NULL, created_at TIMESTAMPTZ NOT NULL, total_on_site_at_snapshot INT NOT NULL. Snapshot creation: INSERT INTO vis_muster_entries SELECT from vis_sign_ins WHERE signed_out_at IS NULL — single batch INSERT.
  3. vis_muster_entries — muster_id UUID FK NOT NULL, sign_in_id UUID FK NOT NULL, visitor_name TEXT NOT NULL (snapshot — frozen at muster creation time), visitor_type TEXT NOT NULL (snapshot), building TEXT (snapshot), status TEXT NOT NULL DEFAULT 'UNKNOWN' 4-value CHECK (UNKNOWN, ACCOUNTED_FOR, EVACUATED, ASSISTANCE_NEEDED). UNIQUE(muster_id, sign_in_id). INDEX(muster_id, status).
Produces → 3 tables. Migration: 097_vis_banned_muster.sql. Total P2-1 tables: 9.
04Seed Data
Seed
What Gets Seeded
  1. 4 visitor types: "Parent" (safeguarding not required, blue badge), "Contractor" (required, amber), "Guest Speaker" (required, green), "Volunteer" (required, purple — links to platform_volunteer_profiles per ADR-032).
  2. 5 visitors: 3 parents (returning visitors with email_hash populated), 1 contractor, 1 guest speaker. All with encrypted PII.
  3. 8 sign-ins: 3 currently on-site (signed_out_at IS NULL — for muster testing). 5 historical (completed sign-in/sign-out). Mix of safeguarding statuses: PASSED, NOT_REQUIRED, BYPASSED_BY_ADMIN (with bypass_admin_id + reason).
  4. 1 pre-registration: Guest speaker for Thursday, QR token generated, not yet used.
  5. 1 recurring visitor: Maintenance contractor, Tuesdays + Thursdays 8am–4pm, valid current month.
  6. 1 banned person: "John Doe" COURT_ORDER, effective indefinitely, court order document uploaded. name_hash computed from normalised "john doe" + DOB.
  7. 1 muster snapshot + 3 entries: From last week's fire drill. 3 visitors snapshotted: 2 ACCOUNTED_FOR + 1 EVACUATED.
  8. 1 settings row: require_purpose=true, auto_sign_out_hours=12.
  9. Permissions: SAF-001:read to Teacher, Staff (view visitor log + current on-site). SAF-001:write to Staff (process sign-ins, verify backgrounds, manage pre-registrations). SAF-001:admin to Admin (configure visitor types, banned persons, safeguarding settings). safeguarding_ban:read to Admin only (view banned person details + court orders). Admin gets all via everyFunction.
Produces → Rich visitor demo data with encrypted PII, banned person with HMAC hash, active sign-ins for muster testing. SAF-001 permissions.
05Visitor + Sign-In NestJS Module
Code
Services & Endpoints
  1. VisitorService — POST /visitors (create with PII encryption: email → AES-256 → email_encrypted + HMAC → email_hash; phone → same pattern), GET /visitors/lookup (KIOSK RETURNING-VISITOR: accepts raw email, computes HMAC, SELECT WHERE email_hash = $computed; returns visitor_id + name + type for auto-fill; never returns encrypted fields to the kiosk), GET /visitors/:id (admin: decrypts PII for display). GET /visitors/visitor-types, POST /visitors/visitor-types, PATCH /visitors/visitor-types/:id.
  2. SignInService — POST /visitors/sign-in (KIOSK KEYSTONE: step 1: banned person check via BannedPersonService; step 2: if visitor_type requires safeguarding, validate check status; step 3: create sign-in record; emits vis.visitor.signed_in), POST /visitors/:signInId/sign-out (stamps signed_out_at), GET /visitors/on-site (currently signed-in visitors — uses the partial index WHERE signed_out_at IS NULL for instantaneous query), GET /visitors/log (historical sign-in/out records with date range filter), PATCH /visitors/sign-ins/:id/bypass (admin bypasses safeguarding check — requires bypass_reason >10 chars + bypass_admin_id).
Produces → VisitorModule with 2 services, ~12 endpoints, 1 Kafka emit (vis.visitor.signed_in).
06Pre-Registration + Recurring + Banned Persons NestJS Module
Code
Services & Endpoints
  1. PreRegistrationService — POST /visitors/pre-register (staff creates: generates 32-byte QR token, creates vis_visitors entry if new, creates vis_pre_registrations row, optionally sends email to visitor with QR code), GET /visitors/pre-registrations (upcoming pre-registrations), POST /visitors/pre-register/scan (kiosk scans QR: validates token active + not expired + not used; resolves to visitor + purpose + host; stamps used_at; creates sign-in automatically). DELETE /visitors/pre-registrations/:id (cancel).
  2. RecurringVisitorService — GET /visitors/recurring, POST /visitors/recurring (create schedule with JSONB access_schedule), PATCH /visitors/recurring/:id, GET /visitors/recurring/today (who is expected today based on access_schedule).
  3. BannedPersonService — SAFETY KEYSTONE. POST /visitors/banned-persons (admin creates: normalises name + DOB, computes HMAC → name_hash, stores ban details + document), GET /visitors/banned-persons (admin with safeguarding_ban:read: list with plaintext names), PATCH /visitors/banned-persons/:id (admin reviews, extends, deactivates). POST /visitors/banned-persons/check (KIOSK INTERNAL: called by SignInService on every sign-in; computes HMAC of entered name + DOB; SELECT WHERE name_hash = $computed AND is_active = true; on match: emits vis.banned_person.detected + returns BLOCKED).
Produces → 3 services, ~12 endpoints, 1 Kafka emit (vis.banned_person.detected).

10Vertical Slice Integration Test
Test
Test Script
  1. Visitor type configuration: Admin creates "Contractor" type with safeguarding required. Verify UNIQUE(school_id, name).
  2. New visitor sign-in: Kiosk: enter name + email. Verify vis_visitors created with encrypted email + HMAC email_hash. Verify sign-in created with safeguarding status.
  3. Returning visitor lookup: Same email at kiosk next week. Verify HMAC lookup returns the existing visitor record. Verify auto-fill works.
  4. Pre-registration + QR scan: Staff pre-registers a speaker. Verify QR token generated. Kiosk: scan QR. Verify pre-reg resolved + used_at stamped + sign-in auto-created. Scan same QR again → 410 (already used).
  5. Safeguarding bypass: Admin bypasses safeguarding for a contractor. Verify bypass_admin_id + bypass_reason (>10 chars) required. Verify bypass_reason <10 chars → 400.
  6. Banned person detection: Add banned person with name + DOB. Compute HMAC. Kiosk: enter matching name + DOB. Verify sign-in BLOCKED. Verify vis.banned_person.detected fires. Verify kiosk shows neutral message (no ban details).
  7. Banned person non-match: Kiosk: enter a name that does NOT match any ban. Verify sign-in proceeds normally.
  8. Emergency muster: 3 visitors currently on-site (signed_out_at IS NULL). Create muster snapshot. Verify 3 vis_muster_entries created with status=UNKNOWN. Mark 2 as ACCOUNTED_FOR + 1 as EVACUATED. Verify summary: 0 unknown, 2 accounted, 1 evacuated.
  9. Sign-out + auto sign-out: Sign out a visitor. Verify signed_out_at stamped. Verify they disappear from the on-site list. Verify auto_sign_out_hours setting (12h).
  10. Visibility: Teacher sees on-site list (SAF-001:read). Cannot access banned persons. Staff can process sign-ins. Admin manages all. Banned person detail requires safeguarding_ban:read.
Produces → Verified visitor lifecycle: kiosk sign-in → returning visitor → pre-reg QR → banned person block → safeguarding bypass → muster snapshot → accountability → sign-out.
