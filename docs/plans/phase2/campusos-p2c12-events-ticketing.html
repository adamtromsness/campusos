P2-12: Events & Ticketing

School event creation with multi-tier pricing, atomic ticket sales with race-condition-proof inventory (UPDATE WHERE quantity_sold+$qty≤quantity — never SELECT-then-UPDATE), Stripe payment integration with pending order expiry cleanup, QR-code ticket generation with gate scanning and audit log, season passes with multi-event inclusion, complimentary entry lists by type (athlete, coach, official, media, VIP), event volunteer signup, and revenue reporting linked to Cycle 6 payments. Sports games, arts performances, fundraisers, and school dances — one ticketing engine for all.
May 2026 · 10 Steps · ERD v11 · M101 Events & Ticketing (9 tables) · ATH-010 + EVT-001 · Phase 2 Cycle 12

Plan Overview

Phase 2 Cycle 12 builds the entire M101 Events & Ticketing module — 9 tables. This is a new module (not a .1 cycle) that provides the school's unified ticketing platform for all event types: athletic games, theatre performances, school dances, fundraiser galas, and graduation ceremonies. Revenue flows through the existing Cycle 6 Payments engine via Stripe.

The technical keystone is the atomic ticket sale: the tier's quantity_sold is incremented inside a single UPDATE WHERE clause, not a SELECT-then-UPDATE pattern. If the row matches (quantity_sold + requested ≤ quantity), the sale succeeds. If zero rows match, the tier is sold out. This eliminates the race condition where two concurrent buyers both see "2 remaining" and both succeed. The event-level CHECK constraint (total_tier_quantity ≤ total_capacity) provides a second layer of venue-level oversell protection maintained by a trigger on evt_ticket_tiers.

Concurrency — Atomic Ticket Sales

The ERD explicitly mandates: UPDATE evt_ticket_tiers SET quantity_sold = quantity_sold + $qty WHERE id = $tier_id AND quantity_sold + $qty ≤ quantity. Never SELECT-then-UPDATE. If the UPDATE returns 0 rows, the tier is sold out — return 409 Conflict. The event-level CHECK(total_capacity IS NULL OR total_tier_quantity ≤ total_capacity) is enforced by a trigger that recalculates total_tier_quantity on every tier change. Gate scanning uses the same pattern: UPDATE evt_tickets SET status='USED', scanned_at=now() WHERE qr_code_token=$1 AND status='VALID'. 0 rows = already scanned or invalid.

Vertical Slice Deliverable

Admin creates "Spring Musical: Grease" event (May 15, 7pm, Auditorium, capacity 300) → 3 tiers: "General Admission" ($10, 200 qty, on sale now), "Reserved Seating" ($15, 80 qty, on sale now), "VIP Front Row" ($25, 20 qty, sale starts May 1) → event status ON_SALE → admin creates comp list: all drama club students (STUDENT), director (STAFF), 2 reviewers (MEDIA) → admin creates "All Sports Season Pass" ($50, includes all home athletic games this year, ACTIVE) → parent purchases 2 General Admission tickets → atomic sale: quantity_sold 0→2, order PENDING with Stripe PaymentIntent, 15-min expiry → Stripe webhook confirms payment → order CONFIRMED → 2 QR-code tickets generated → parent tries to buy 199 more General Admission → atomic UPDATE succeeds for 198 (quantity 200, sold 200) → 199th attempt: 0 rows → 409 Sold Out → event auto-flips to SOLD_OUT → event night: gate volunteer scans QR → atomic UPDATE → VALID → evt_ticket_scans logged → same QR scanned again → 0 rows → ALREADY_SCANNED → logged → comp list person arrives → name on list → waved through, scan logged as COMP → season pass holder arrives → pass validated (event in events_included array) → admitted → meanwhile, another parent's PENDING order expires (15 min) → OrderExpiryWorker: cancel order, decrement quantity_sold, cancel Stripe intent → tier reopens → after event: admin marks COMPLETED → revenue report: $X gross, $Y Stripe fees, $Z net → evt.event.completed fires → GLConsumer posts revenue journal entry.

What's In / What's Deferred

In scope (9 tables): evt_events, evt_ticket_tiers, evt_orders, evt_tickets, evt_volunteers, evt_ticket_scans, evt_season_passes, evt_comp_lists, evt_refunds. Functions ATH-010 (Athletic Ticketing) + EVT-001 (School Events).

Deferred: Reserved seating map (seat picker UI). Multi-date recurring events (series). Ticket transfer between holders. Waitlist for sold-out tiers. Third-party ticketing platform integration (Eventbrite). Digital wallet ticket (Apple/Google Wallet pass). Event promotion via Cycle 14 Communications. Event-linked fundraising goals.

Step-by-Step Build Plan

01Events + Tiers + Orders Schema (5 tables)
Schema
  1. evt_events — school_id UUID NOT NULL, title TEXT NOT NULL, description TEXT, event_type TEXT NOT NULL 8-value CHECK (ATHLETIC_GAME, PERFORMANCE, DANCE, FUNDRAISER, GRADUATION, ASSEMBLY, COMMUNITY, OTHER), event_date DATE NOT NULL, start_time TIME NOT NULL, end_time TIME, venue_id UUID FK(fac_spaces) nullable, venue_name TEXT, total_capacity INT, total_tier_quantity INT DEFAULT 0 (maintained by trigger on evt_ticket_tiers), linked_game_id UUID (soft to ath_games), status TEXT NOT NULL DEFAULT 'DRAFT' 5-value CHECK (DRAFT, ON_SALE, SOLD_OUT, COMPLETED, CANCELLED), created_by UUID FK NOT NULL. CHECK(total_capacity IS NULL OR total_tier_quantity ≤ total_capacity). INDEX(school_id, event_date, status).
  2. evt_ticket_tiers — event_id UUID FK NOT NULL, name TEXT NOT NULL, price NUMERIC(8,2) NOT NULL, quantity INT NOT NULL, quantity_sold INT NOT NULL DEFAULT 0, sale_starts_at TIMESTAMPTZ, sale_ends_at TIMESTAMPTZ, is_active BOOLEAN DEFAULT true. Partial INDEX(event_id, sale_starts_at, sale_ends_at) WHERE is_active=true. ATOMIC SALE: UPDATE SET quantity_sold=quantity_sold+$qty WHERE id=$1 AND quantity_sold+$qty≤quantity. Trigger: on INSERT/UPDATE/DELETE → recalculate parent event.total_tier_quantity = SUM(quantity).
  3. evt_orders — event_id UUID FK NOT NULL, purchaser_id UUID FK(iam_person) NOT NULL, status TEXT NOT NULL DEFAULT 'PENDING' 4-value CHECK (PENDING, CONFIRMED, CANCELLED, REFUNDED), total_amount NUMERIC(8,2) NOT NULL, stripe_payment_intent_id TEXT, expires_at TIMESTAMPTZ (PENDING orders expire; OrderExpiryWorker every 5 min), confirmed_at TIMESTAMPTZ, cancelled_at TIMESTAMPTZ. Partial INDEX(expires_at) WHERE status='PENDING'. On CANCEL: decrement tier.quantity_sold for each ticket. Emits evt.order.confirmed.
  4. evt_tickets — order_id UUID FK NOT NULL, tier_id UUID FK NOT NULL, holder_name TEXT, qr_code_token TEXT NOT NULL UNIQUE, status TEXT NOT NULL DEFAULT 'VALID' 4-value CHECK (VALID, USED, CANCELLED, REFUNDED), scanned_at TIMESTAMPTZ. GATE SCAN ATOMIC: UPDATE SET status='USED', scanned_at=now() WHERE qr_code_token=$1 AND status='VALID'. 0 rows = already used or invalid. INDEX(qr_code_token).
  5. evt_refunds — order_id UUID FK NOT NULL, refund_amount NUMERIC(8,2) NOT NULL, reason TEXT NOT NULL, stripe_refund_id TEXT, refunded_by UUID FK NOT NULL, refunded_at TIMESTAMPTZ NOT NULL. On INSERT: order.status=REFUNDED, tickets.status=REFUNDED, tier.quantity_sold decremented. Emits evt.refund.issued for GL posting.
Produces → 5 tables + tier quantity trigger. Migration: 126_evt_events_orders.sql.
02Scans + Season Passes + Comp Lists + Volunteers Schema (4 tables)
Schema
  1. evt_ticket_scans — ticket_id UUID FK(evt_tickets) NOT NULL, scanned_at TIMESTAMPTZ NOT NULL, scanned_by UUID FK NOT NULL, scan_result TEXT NOT NULL 4-value CHECK (VALID, ALREADY_SCANNED, INVALID, EXPIRED). RANGE partition by scanned_at MONTHLY. Gate audit log — every scan attempt recorded regardless of result.
  2. evt_season_passes — school_id UUID NOT NULL, person_id UUID FK(iam_person) NOT NULL, pass_type TEXT NOT NULL, events_included UUID[] (array of evt_event IDs; null = all events of matching type), price NUMERIC(8,2) NOT NULL, purchased_at TIMESTAMPTZ, stripe_payment_intent_id TEXT, status TEXT NOT NULL DEFAULT 'ACTIVE' 3-value CHECK (ACTIVE, EXPIRED, REVOKED), academic_year TEXT NOT NULL. INDEX(school_id, person_id, academic_year). At gate: verify pass ACTIVE + event in events_included (or null = all).
  3. evt_comp_lists — event_id UUID FK(evt_events) NOT NULL, comp_type TEXT NOT NULL 8-value CHECK (ATHLETE, COACH, OFFICIAL, MEDIA, STAFF, STUDENT, VIP, OTHER), person_id UUID FK(iam_person), added_by UUID FK NOT NULL. UNIQUE(event_id, comp_type, person_id). Comp list members bypass ticketing at the gate.
  4. evt_volunteers — event_id UUID FK NOT NULL, person_id UUID FK(iam_person) NOT NULL, role TEXT (gate volunteer, usher, concessions, setup, cleanup), status TEXT NOT NULL DEFAULT 'SIGNED_UP' 3-value CHECK (SIGNED_UP, CONFIRMED, CANCELLED), check_in_at TIMESTAMPTZ. UNIQUE(event_id, person_id).
Produces → 4 tables. Migration: 127_evt_scans_passes.sql. Total P2-12 tables: 9.

04Event + Tier + Order NestJS Module
Code
  1. EventService — CRUD for events. GET /events (public: ON_SALE events with tier availability), POST /events, PATCH /events/:id (status transitions: DRAFT → ON_SALE → SOLD_OUT → COMPLETED). Auto-detect SOLD_OUT: when all tiers have quantity_sold = quantity. POST /events/:id/complete (emits evt.event.completed for GL revenue posting).
  2. TierService — POST /events/:id/tiers, PATCH /events/tiers/:id. Trigger maintains event.total_tier_quantity.
  3. OrderService — POST /events/:eventId/purchase (ATOMIC: for each tier/qty pair: UPDATE quantity_sold WHERE +$qty ≤ quantity → 0 rows = 409 Sold Out; creates order PENDING with expires_at = now()+15min; creates Stripe PaymentIntent; creates tickets with QR tokens), GET /events/orders/my (purchaser: own orders + tickets), POST /events/orders/:id/confirm (Stripe webhook callback). OrderExpiryWorker: every 5 min, finds PENDING WHERE expires_at < now() → cancel order, decrement tier.quantity_sold, cancel Stripe intent.
  4. RefundService — POST /events/orders/:id/refund (full or partial; Stripe refund; tickets → REFUNDED; tier.quantity_sold decremented; emits evt.refund.issued).
Produces → 4 services + 1 worker (OrderExpiryWorker), ~14 endpoints, 3 Kafka emits.
05Gate Scanning + Season Pass + Comp List + Volunteer NestJS Module
Code
  1. GateScanService — POST /events/gate/scan (ATOMIC: UPDATE evt_tickets SET status='USED' WHERE qr_code_token=$1 AND status='VALID'; if 0 rows: check if ALREADY_SCANNED (status='USED'), INVALID (no such token), or EXPIRED; log every attempt to evt_ticket_scans regardless of result; return scan_result). Rate-limited per event per scanner device.
  2. SeasonPassService — POST /events/season-passes (purchase with Stripe), GET /events/season-passes/my, POST /events/gate/season-pass-check (at gate: verify pass ACTIVE + event in events_included or events_included IS NULL; log scan).
  3. CompListService — GET /events/:id/comp-list, POST /events/:id/comp-list (bulk add by type), DELETE /events/:id/comp-list/:entryId. POST /events/gate/comp-check (at gate: verify person on comp list for this event).
  4. VolunteerService — POST /events/:id/volunteers (sign up), GET /events/:id/volunteers, PATCH /events/volunteers/:id (confirm/cancel/check-in).
Produces → 4 services, ~14 endpoints. Total P2-12 endpoints: ~28.

07Vertical Slice Integration Test
Test
  1. Atomic ticket sale: Create tier qty=5. Purchase 3 (quantity_sold=3). Purchase 3 more → only 2 succeed (atomic UPDATE: 3+3>5 → 0 rows for 1 ticket). Verify 409 returned. Verify quantity_sold=5.
  2. Concurrent sale race condition: Tier qty=1. Two simultaneous purchases. Exactly one succeeds, one gets 409. No oversell.
  3. Event capacity CHECK: Event capacity=10. Create tiers totalling 12 → trigger should prevent (total_tier_quantity > total_capacity).
  4. Order expiry: Create PENDING order with 1-minute expiry. Wait. OrderExpiryWorker fires. Verify order CANCELLED, quantity_sold decremented, Stripe intent cancelled.
  5. Gate scan atomic: Scan valid QR → VALID, status=USED, scanned_at stamped. Scan same QR → ALREADY_SCANNED. Scan unknown QR → INVALID. All 3 logged to evt_ticket_scans.
  6. Season pass: Purchase pass with events_included=[event_A, event_B]. Gate check for event_A → admitted. Gate check for event_C (not included) → denied.
  7. Comp list: Add 3 athletes to comp list. Gate comp-check for athlete → admitted. Gate comp-check for non-listed person → denied.
  8. Refund: Refund confirmed order. Verify tickets REFUNDED, tier.quantity_sold decremented, Stripe refund created, evt.refund.issued fires.
  9. Auto SOLD_OUT: Sell all tickets across all tiers. Verify event status auto-flips to SOLD_OUT.
  10. Visibility: Public sees ON_SALE events. Parent buys tickets + views own. Gate volunteer scans (EVT-001:write). Admin manages all + views revenue.
Produces → Verified events lifecycle: create → sell (atomic) → expire → gate scan (atomic) → season pass → comp list → refund → complete → GL posting.
08Stripe Integration

On payment_intent.payment_failed: order → CANCELLED, tier decremented. Season pass purchases use the same flow. Refunds use Stripe Refund API.
