Cycle 14: Communications
& Messaging

Threaded messaging between teachers, parents, and staff with role-based thread types, school-wide announcements with pre-computed audience fan-out, emergency alerts with multi-channel delivery tracking, and three-tier content moderation (platform + district + building). Opens Wave 3.
May 2026 · 10 Steps · ERD v11 · M40 Communications (29 tables — 15 new in scope, ~12 already built in Cycle 3) · Opens Wave 3

Plan Overview

Cycle 14 completes the M40 Communications module that Cycle 3 partially built. Cycle 3 shipped the notification infrastructure (queue, preferences, push tokens) and calendar surface. Cycle 14 adds the 15 remaining tables covering threaded messaging, announcements, emergency alerts, and content moderation. This is the first cycle where every authenticated user — teachers, parents, students, staff, and administrators — is a first-class participant in the core workflow (sending and receiving messages). Prior cycles had per-persona surfaces; messaging is universal.

The ERD specifies HASH partitioning (64 buckets) on msg_threads and msg_thread_participants (ADR-047) plus RANGE monthly partitioning on msg_messages for districts at scale (250M messages/month). This cycle ships the tables as simple (non-partitioned) tables with the correct indexes. Partitioning is a Phase 3 ops concern activated before pilot at scale — the schema, indexes, and query patterns are designed partition-ready from day one so the migration is a CREATE TABLE ... PARTITION BY swap with no application-layer changes.

Safety — Content Moderation

Every outbound message passes through the three-tier content moderation pipeline before delivery. Platform-level keywords (non-negotiable) + district-level + building-level policies are evaluated in most-restrictive-wins order. Actions: BLOCK (message rejected with user-facing explanation), FLAG_FOR_REVIEW (delivered but queued for admin review), ESCALATE_TO_COUNSELLOR (delivered + counsellor notified — integrates with Cycle 11's coordinated care surface). The moderation log is immutable for compliance audit.

Vertical Slice Deliverable

Teacher Rivera creates a TEACHER_PARENT thread with Maya's parent (David Chen) to discuss Maya's progress → sends a message with a text attachment → content moderation clears the message (no keyword matches) → David sees the message in his inbox with an unread badge → David replies → Rivera marks the reply as read → admin publishes a school-wide announcement "Spring Concert Friday" with audience=ALL_SCHOOL → announcement worker pre-computes the audience list (all active users) → David sees the announcement in his feed → admin issues an EMERGENCY alert "Severe Weather Shelter-in-Place" → multi-channel delivery fans out (PUSH + APP) → teachers acknowledge the alert → admin resolves the alert.

In scope (15 tables): msg_thread_types, msg_threads, msg_thread_participants, msg_thread_stats, msg_messages, msg_message_reads, msg_message_attachments, msg_announcements, msg_announcement_audiences, msg_announcement_reads, msg_alert_types, msg_emergency_alerts, msg_emergency_alert_deliveries, msg_moderation_policies, msg_moderation_log. Functions COM-001 through COM-004.

Deferred: HASH partitioning on threads/participants (ADR-047, simple table now). RANGE monthly on messages (simple table now). Redis ZSET unread counters (in-memory counts this cycle). msg_templates (template engine for transactional messages). msg_emission_log (Kafka compacted topic). Recurring announcements (iCal RRULE processing). Route-targeted announcements (requires M61 Transportation). AI content moderation sensitivity scoring (keyword match only this cycle).

Step-by-Step Build Plan

01 Messaging Schema — Threads + Messages + Reads
Schema

The core messaging infrastructure: configurable thread types, the thread + participant model, per-thread statistics for inbox rendering, individual messages with read tracking, and file attachments.

Tables (7)
  1. msg_thread_types — school_id UUID, name TEXT NOT NULL, allowed_participant_roles TEXT[], is_system BOOLEAN DEFAULT false. UNIQUE(school_id, name). System types seeded: TEACHER_PARENT, CLASS_DISCUSSION, ADMIN_STAFF, STAFF_ONLY, STUDENT_TEACHER.
  2. msg_threads — school_id UUID NOT NULL, thread_type_id UUID FK, subject TEXT, created_by UUID FK(platform_users), is_archived BOOLEAN DEFAULT false, created_at TIMESTAMPTZ. INDEX(school_id, created_at DESC). Partition-ready: designed for HASH(school_id) 64 buckets per ADR-047 but ships as a simple table this cycle.
  3. msg_thread_participants — thread_id UUID FK NOT NULL, platform_user_id UUID NOT NULL (soft to platform_users), school_id UUID NOT NULL, is_muted BOOLEAN DEFAULT false, joined_at TIMESTAMPTZ. UNIQUE(platform_user_id, thread_id, school_id). INDEX(platform_user_id, school_id, thread_id) for inbox query. Partition-ready: same HASH(school_id) as msg_threads for efficient JOINs.
  4. msg_thread_stats — Denormalised per-thread summary. thread_id UUID FK UNIQUE, message_count INT DEFAULT 0, last_message_at TIMESTAMPTZ, last_message_preview TEXT (first 100 chars). Updated by Kafka consumer on msg.message.posted. Inbox renders from this + the participants join without scanning msg_messages.
  5. msg_messages — thread_id UUID FK NOT NULL, school_id UUID NOT NULL (denormalised for partition-ready queries), sender_id UUID NOT NULL (soft to platform_users), body TEXT NOT NULL, is_moderated BOOLEAN DEFAULT false, moderation_status TEXT DEFAULT 'APPROVED' 3-value CHECK (APPROVED, BLOCKED, FLAGGED), created_at TIMESTAMPTZ NOT NULL DEFAULT now(). INDEX(thread_id, created_at DESC). Partition-ready: designed for RANGE(created_at) monthly per ADR-047 but ships as simple table.
  6. msg_message_reads — message_id UUID FK NOT NULL, reader_id UUID NOT NULL (soft to platform_users). UNIQUE(message_id, reader_id). read_at TIMESTAMPTZ. The unread badge count in the inbox is derived from messages without a matching read row for the calling user.
  7. msg_message_attachments — message_id UUID FK NOT NULL, filename TEXT NOT NULL, s3_key TEXT NOT NULL, file_size_bytes INT, mime_type TEXT. Signed S3 URLs with 15–60 min expiry generated at read time by the Step 4 service.
Produces → 7 new tables. Migration: 049_msg_threads_messages.sql.
02 Announcements + Alerts + Moderation Schema
Schema

School-wide announcements with pre-computed audience fan-out, emergency alerts with multi-channel delivery tracking and acknowledgement, and the three-tier content moderation policy system.

Tables (8)
  1. msg_announcements — school_id UUID, author_id UUID FK, title TEXT, body TEXT NOT NULL, publish_at TIMESTAMPTZ, expires_at TIMESTAMPTZ, audience_type TEXT NOT NULL 6-value CHECK (ALL_SCHOOL, CLASS, YEAR_GROUP, ROLE, ROUTE, CUSTOM), is_recurring BOOLEAN DEFAULT false, recurrence_rule TEXT nullable, parent_announcement_id UUID FK nullable. INDEX(school_id, publish_at DESC). The audience worker pre-computes delivery rows in msg_announcement_audiences on publish.
  2. msg_announcement_audiences — Pre-computed delivery rows. announcement_id UUID FK NOT NULL, platform_user_id UUID NOT NULL, delivery_status TEXT DEFAULT 'PENDING' 3-value CHECK (PENDING, DELIVERED, FAILED). INDEX(platform_user_id, delivery_status). Populated by the announcement publish worker.
  3. msg_announcement_reads — announcement_id UUID FK NOT NULL, reader_id UUID NOT NULL. UNIQUE(announcement_id, reader_id). read_at TIMESTAMPTZ.
  4. msg_alert_types — School-configurable alert severity definitions. school_id UUID, name TEXT NOT NULL, severity TEXT NOT NULL 4-value CHECK (INFO, WARNING, URGENT, EMERGENCY), default_channels TEXT[], requires_acknowledgement BOOLEAN DEFAULT false.
  5. msg_emergency_alerts — school_id UUID, alert_type_id UUID FK, title TEXT NOT NULL, body TEXT NOT NULL, issued_by UUID FK, incident_id UUID nullable (soft to inc_incidents), issued_at TIMESTAMPTZ, status TEXT NOT NULL DEFAULT 'ACTIVE' 2-value CHECK (ACTIVE, RESOLVED). INDEX(school_id, issued_at DESC). Emits msg.emergency.issued on creation.
  6. msg_emergency_alert_deliveries — Multi-channel delivery tracking per recipient. alert_id UUID FK NOT NULL, recipient_id UUID NOT NULL, channel TEXT NOT NULL 4-value CHECK (PUSH, SMS, EMAIL, APP), status TEXT NOT NULL DEFAULT 'PENDING' 4-value CHECK (PENDING, SENT, DELIVERED, FAILED), sent_at TIMESTAMPTZ, acknowledged_at TIMESTAMPTZ nullable. UNIQUE(alert_id, recipient_id, channel).
  7. msg_moderation_policies — Three-tier content moderation. scope TEXT NOT NULL 3-value CHECK (PLATFORM, DISTRICT, BUILDING), scope_id UUID nullable (null for PLATFORM), keywords TEXT[] NOT NULL, keyword_action TEXT NOT NULL 3-value CHECK (BLOCK, FLAG_FOR_REVIEW, ESCALATE_TO_COUNSELLOR), sensitivity_threshold NUMERIC(3,2), escalation_rules JSONB, is_active BOOLEAN DEFAULT true. Most restrictive action wins across tiers.
  8. msg_moderation_log — IMMUTABLE audit. message_id UUID FK NOT NULL, policy_id UUID FK NOT NULL, flag_type TEXT NOT NULL 4-value CHECK (BLOCKED, FLAGGED_FOR_REVIEW, ESCALATED_TO_COUNSELLOR, AUTO_APPROVED), matched_keywords TEXT[], review_outcome TEXT nullable 3-value CHECK (CONFIRMED_BLOCK, RELEASED, ESCALATED), reviewed_at TIMESTAMPTZ nullable. No UPDATE on core fields. Service-side discipline.
Produces → 8 new tables. Migration: 050_msg_announcements_alerts_moderation.sql. Total Cycle 14 tables: 15.

06 Content Moderation NestJS Module
Code
Services & Endpoints
  1. ModerationService — Internal pipeline called by MessageService.send() before every message INSERT. evaluateMessage(schoolId, messageBody) loads all active policies for the three tiers (PLATFORM + DISTRICT where scope_id matches the school's district + BUILDING where scope_id = schoolId), scans the message body against each policy's keyword list (case-insensitive substring match), collects all matches, applies the most-restrictive-wins rule (BLOCK > ESCALATE_TO_COUNSELLOR > FLAG_FOR_REVIEW > AUTO_APPROVED), writes an immutable msg_moderation_log row per evaluated policy, and returns the final action. BLOCK prevents the INSERT; FLAG stamps the message row with moderation_status='FLAGGED' + adds to the admin review queue; ESCALATE does FLAG + emits a notification to the school counsellor via the Cycle 3 notification queue.
  2. ModerationPolicyService — GET /messaging/moderation-policies (admin: policies for this school across all tiers), POST /messaging/moderation-policies (admin creates building-level policy), PATCH /messaging/moderation-policies/:id (update keywords, action, active flag). Platform-tier policies are seed-only (admin cannot edit).
  3. ModerationReviewService — GET /messaging/moderation-queue (admin: flagged messages pending review), PATCH /messaging/moderation-log/:id/review (admin: CONFIRMED_BLOCK or RELEASED; RELEASED restores the message to visible state).
Produces → 3 services, ~6 endpoints. Total Cycle 14 endpoints: ~28.
07 Messaging UI — Inbox + Thread + Compose
UI
Pages
  1. Inbox /messages — "Messages" app tile gated on COM-001:read (universal). Thread list sorted by last_message_at DESC. Per-row: participants (avatars or names), subject, last message preview (from msg_thread_stats), relative timestamp, unread dot. Compose button opens new-thread modal.
  2. Thread View /messages/threads/:id — message list (newest at bottom, scroll-to-latest). Per-message: sender name, timestamp, body, attachment links (signed URLs). Read receipts indicator.   3. Compose Modal — thread type picker (shows types where actor's role is in allowed_participant_roles), participant search (searches platform_users in the school), subject, initial message body, optional attachment.
Produces → "Messages" app tile + inbox, thread view, compose modal. The first universal-participation UI surface.
08 Announcements + Alerts UI
UI
Pages

09 Admin Moderation UI
UI
Pages
  1. Moderation Policy Editor /messages/moderation — admin: policies grouped by tier (PLATFORM read-only / DISTRICT / BUILDING). Per-policy: keywords list, action pill (BLOCK rose / FLAG amber / ESCALATE purple), active/inactive toggle. Create building-level policy form.
  2. Flagged Message Queue /messages/moderation/queue — admin: messages with moderation_status=FLAGGED. Per-row: sender, thread, matched keywords, flagging policy, message preview. Release / Confirm Block buttons.
  3. Moderation Log /messages/moderation/log — admin: immutable audit trail. Filters by flag_type, date range, policy. Per-row: message preview, matched keywords, action taken, review outcome (when reviewed).
Produces → Moderation policy editor, flagged queue, audit log.
10 Vertical Slice Integration Test
Test
Test Script
  1. Thread creation + message send: Rivera creates TEACHER_PARENT thread with David Chen. Sends message about Maya's progress. Verify msg_thread_stats updated. Verify msg.message.posted fires.
  2. Content moderation pipeline: Rivera sends a message containing a PLATFORM-tier blocked keyword. Verify BLOCK action prevents delivery. Verify moderation_log row created. Rivera sends a message containing a BUILDING-tier flagged keyword. Verify FLAG action allows delivery but queues for review.
  3. Read receipts + unread count: David reads Rivera's first message. Verify read receipt row. Verify unread count decrements. Rivera checks unread badge shows 0 for this thread.
  4. Parent reply: David replies in the thread. Verify Rivera sees the reply. Thread stats update (message_count + last_message_preview).
  5. Announcement publish + audience: Admin publishes ALL_SCHOOL announcement. Verify audience rows pre-computed for all active users. David sees it in feed. David marks read.
  6. Emergency alert lifecycle: Admin issues EMERGENCY "Shelter in Place". Verify delivery rows fanned out per recipient × channel. Rivera acknowledges. Admin checks delivery stats (1 acknowledged out of N). Admin resolves.
  7. Moderation admin review: Admin reviews the flagged message from S2. Releases it. Verify moderation_log.review_outcome = RELEASED. Message now visible to recipient.
  8. Thread type role constraints: Student attempts to create ADMIN_STAFF thread. Verify 403 (role not in allowed_participant_roles). Student creates STUDENT_TEACHER thread. Verify 201.
  9. Visibility: Parent sees own threads + announcements + emergency alerts. Cannot see other parents' threads. Cannot issue alerts or publish announcements. Student sees own threads + announcements. Cannot access moderation endpoints.
  10. Escalation to counsellor: A message matches an ESCALATE_TO_COUNSELLOR policy keyword. Verify FLAG + notification queued for the school counsellor via Cycle 3 notification queue.
Produces → Verified messaging lifecycle: thread → message → moderation → read → reply → announcement → emergency alert → admin review.
