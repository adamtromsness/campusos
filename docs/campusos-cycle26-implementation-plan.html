Accounting

The financial system of record: chart of accounts with fund accounting, double-entry general ledger with DB-validated balanced batches (ADR-058/059), Kafka consumer that auto-posts GL entries from Cycle 6 payment events, accounting period controls with LOCKED permanence, budget management with encumbrance tracking, accounts payable with supplier invoices + three-way match readiness, bank reconciliation, and board-ready financial report snapshots. May 2026 · 10 Steps · ERD v11 · M83 Finance (9 pre-staged + 5 new = 14 tables — all in scope) · ADR-038/051/058/059 · FIN-001 through FIN-004 · Opens Wave 6

Plan Overview

Cycle 26 builds the M83 Finance & Accounting module — all 14 tables. 9 tables were pre-documented under M81 per ADR-051/058 (the GL backbone designed alongside the Cycle 6 payment system to validate the M84→M83 event integration contract). 5 additional tables complete the module: AP vouchers, AP payments, reconciliation runs, board report snapshots, and grants. This cycle activates the fin_ tables that have been structurally ready since Wave 1 — the Kafka consumer that converts payment events into double-entry GL entries is the keystone.

This is the most financially critical module in CampusOS. The validate_batch_balance(batch_id) DB procedure (ADR-059) ensures every journal batch balances to zero before it can be posted — the debits must equal the credits at the database level, not just the application level. Accounting periods can be LOCKED permanently by the CFO — no further posting is possible, not even by a platform admin. The fund accounting model supports the 6 GASB fund types that government-funded schools require.

Financial Integrity — Double-Entry Enforcement (ADR-059)

fin_journal_batches uses a DB-level balance validation procedure rather than application-maintained header totals. The PostingService writes all fin_gl_entries debit/credit lines, then calls validate_batch_balance(batch_id) which aggregates actual rows and verifies SUM(debit) = SUM(credit). Only after validation does the batch status flip to POSTED — all inside one transaction. If any entry is missing or the batch doesn't balance, the entire transaction rolls back. The source_event_id UNIQUE index on journal batches provides Kafka consumer idempotency — a redelivered payment event cannot create a duplicate posting.

Vertical Slice Deliverable

CFO configures the chart of accounts (Assets: 1000 Cash, 1100 AR; Liabilities: 2000 AP; Revenue: 4000 Tuition, 4100 Fees; Expenses: 5000 Supplies, 5100 Salaries) with GENERAL fund → opens fiscal year 2025-2026 with 12 accounting periods (Jul–Jun) → sets budget: Revenue $500K, Expenses $480K across 10 budget lines → Cycle 6 payment event pay.payment.received fires (family pays $3,500 tuition) → GL Consumer auto-posts a balanced journal batch: DEBIT 1000 Cash $3,500 + CREDIT 4000 Tuition Revenue $3,500 → validate_batch_balance confirms SUM(debit) = SUM(credit) → batch status = POSTED → budget actuals update → CFO receives a vendor invoice for $1,200 supplies → creates an AP voucher linked to fin_suppliers → approves payment → AP payment posts: DEBIT 5000 Supplies $1,200 + CREDIT 1000 Cash $1,200 → CFO runs monthly bank reconciliation matching GL cash balance to bank statement → generates board report snapshot for the finance committee → CFO locks July accounting period — permanently sealed, no further posting possible.

Step-by-Step Build Plan

01Chart of Accounts + Funds + Periods Schema
Schema

The accounting foundation: hierarchical chart of accounts with 5 account types, GASB fund classifications, and fiscal period controls with permanent LOCK capability.

Tables (3)
  1. fin_chart_of_accounts — school_id UUID, account_code TEXT NOT NULL, account_name TEXT NOT NULL, account_type TEXT NOT NULL 5-value CHECK (ASSET, LIABILITY, EQUITY, REVENUE, EXPENSE), normal_balance TEXT NOT NULL 2-value CHECK (DEBIT, CREDIT), parent_account_id UUID FK nullable (self-referential hierarchy), fund_id UUID FK, is_system BOOLEAN DEFAULT false (protected control accounts: Cash, AR, AP), is_active BOOLEAN DEFAULT true. UNIQUE(school_id, account_code). INDEX(school_id, account_type, is_active).
  2. fin_funds — school_id UUID, fund_code TEXT NOT NULL, fund_name TEXT NOT NULL, fund_type TEXT NOT NULL 6-value CHECK (GENERAL, SPECIAL_REVENUE, CAPITAL_PROJECTS, DEBT_SERVICE, PERMANENT, ENTERPRISE), is_active BOOLEAN DEFAULT true. UNIQUE(school_id, fund_code). The 6 GASB fund types cover government-funded school reporting requirements.
  3. fin_accounting_periods — school_id UUID, fiscal_year TEXT NOT NULL, period_number INT NOT NULL, period_name TEXT NOT NULL, start_date DATE NOT NULL, end_date DATE NOT NULL, status TEXT NOT NULL DEFAULT 'FUTURE' 4-value CHECK (FUTURE, OPEN, CLOSED, LOCKED). LOCKED is permanent — no further posting, no reversal, no override. UNIQUE(school_id, fiscal_year, period_number). The PostingService refuses any entry where the target period is CLOSED or LOCKED.
Produces → 3 tables. Migration: 080_fin_chart_accounts.sql.
02Journal Batches + GL Entries + Balance Validation
Schema

The double-entry engine: atomic journal batches with DB-validated balance enforcement (ADR-058/059), individual debit/credit GL entry lines, and the validate_batch_balance() stored procedure.

Tables (2) + 1 DB procedure
  1. fin_journal_batches — school_id UUID, batch_number TEXT NOT NULL, description TEXT NOT NULL, batch_type TEXT NOT NULL 5-value CHECK (MANUAL, AUTO_PAYMENT, AUTO_INVOICE, AUTO_REFUND, ADJUSTMENT), source_module TEXT (e.g., "payments", "food-service", "library"), source_event_id UUID UNIQUE (Kafka event_id — idempotency key; prevents duplicate posting on redelivery), accounting_period_id UUID FK NOT NULL, posted_by UUID FK, posted_at TIMESTAMPTZ, status TEXT NOT NULL DEFAULT 'DRAFT' 3-value CHECK (DRAFT, POSTED, VOIDED). INDEX(school_id, status, posted_at DESC). UNIQUE(source_event_id) WHERE source_event_id IS NOT NULL.
  2. fin_gl_entries — batch_id UUID FK NOT NULL, account_id UUID FK(fin_chart_of_accounts) NOT NULL, fund_id UUID FK NOT NULL, debit NUMERIC(12,2) NOT NULL DEFAULT 0 CHECK(≥0), credit NUMERIC(12,2) NOT NULL DEFAULT 0 CHECK(≥0), description TEXT, reference_type TEXT nullable, reference_id UUID nullable (soft to pay_invoices, fin_ap_vouchers, etc.). CHECK(debit > 0 OR credit > 0) — every line must have at least one non-zero side. INDEX(batch_id). INDEX(account_id, fund_id) for account balance queries.
  3. validate_batch_balance() — DB PROCEDURE (ADR-059). SELECT SUM(debit) AS total_debit, SUM(credit) AS total_credit FROM fin_gl_entries WHERE batch_id = $1. Returns TRUE when total_debit = total_credit AND total_debit > 0 (non-empty batch). The PostingService calls this inside the same transaction as the status flip to POSTED. RAISE EXCEPTION on imbalance rolls back the entire transaction.
Produces → 2 tables + 1 stored procedure. Migration: 081_fin_gl_entries.sql.
03Budgets + AP + Reconciliation + Board Reports + Grants
Schema

Budget management with per-line tracking and variance analysis, accounts payable with supplier invoice vouchers and payment records, bank reconciliation runs, board-ready financial report snapshots, and grant tracking.

Tables (7)
  1. fin_budgets — school_id UUID, fiscal_year TEXT NOT NULL, fund_id UUID FK, name TEXT NOT NULL, total_revenue NUMERIC(12,2), total_expense NUMERIC(12,2), status TEXT NOT NULL DEFAULT 'DRAFT' 3-value CHECK (DRAFT, APPROVED, AMENDED). UNIQUE(school_id, fiscal_year, fund_id, name).
  2. fin_budget_lines — budget_id UUID FK NOT NULL, account_id UUID FK(fin_chart_of_accounts) NOT NULL, budgeted_amount NUMERIC(12,2) NOT NULL, actual_amount NUMERIC(12,2) DEFAULT 0, encumbered_amount NUMERIC(12,2) DEFAULT 0, remaining_amount NUMERIC(12,2) (computed: budgeted - actual - encumbered). UNIQUE(budget_id, account_id). Updated on every GL posting that hits the mapped account.
  3. fin_ap_vouchers — school_id UUID, supplier_id UUID FK(fin_suppliers) NOT NULL, voucher_number TEXT NOT NULL, invoice_number TEXT, invoice_date DATE NOT NULL, due_date DATE NOT NULL, total_amount NUMERIC(12,2) NOT NULL, gl_account_id UUID FK, fund_id UUID FK, status TEXT NOT NULL DEFAULT 'PENDING' 5-value CHECK (PENDING, APPROVED, PAID, VOIDED, ON_HOLD), approved_by UUID FK, approved_at TIMESTAMPTZ. UNIQUE(school_id, voucher_number). INDEX(school_id, status, due_date).
  4. fin_ap_payments — voucher_id UUID FK NOT NULL, payment_method TEXT NOT NULL 4-value CHECK (CHECK, ACH, WIRE, CREDIT_CARD), payment_reference TEXT, amount NUMERIC(12,2) NOT NULL, paid_at TIMESTAMPTZ NOT NULL, paid_by UUID FK NOT NULL, journal_batch_id UUID FK (links to the GL posting). INDEX(voucher_id).
  5. fin_reconciliation_runs — school_id UUID, account_id UUID FK(fin_chart_of_accounts) NOT NULL (typically the Cash account), period_id UUID FK NOT NULL, gl_balance NUMERIC(12,2) NOT NULL, bank_balance NUMERIC(12,2) NOT NULL, difference NUMERIC(12,2) NOT NULL, outstanding_items JSONB, status TEXT NOT NULL DEFAULT 'IN_PROGRESS' 3-value CHECK (IN_PROGRESS, RECONCILED, VARIANCE_FLAGGED), reconciled_by UUID FK, reconciled_at TIMESTAMPTZ. INDEX(school_id, period_id).
  6. fin_board_report_snapshots — school_id UUID, report_type TEXT NOT NULL 4-value CHECK (BALANCE_SHEET, INCOME_STATEMENT, BUDGET_VS_ACTUAL, CASH_FLOW), period_id UUID FK, generated_at TIMESTAMPTZ NOT NULL, generated_by UUID FK NOT NULL, report_data JSONB NOT NULL (frozen snapshot of the numbers at generation time), s3_key TEXT nullable (PDF rendering deferred). IMMUTABLE once generated.
  7. fin_grants — school_id UUID, fund_id UUID FK, grant_name TEXT NOT NULL, grantor TEXT NOT NULL, award_amount NUMERIC(12,2) NOT NULL, start_date DATE NOT NULL, end_date DATE NOT NULL, drawn_amount NUMERIC(12,2) DEFAULT 0, remaining_amount NUMERIC(12,2), status TEXT NOT NULL DEFAULT 'ACTIVE' 3-value CHECK (ACTIVE, CLOSED, REPORTING). INDEX(school_id, status).
Produces → 7 tables. Migration: 082_fin_budgets_ap.sql. Total Cycle 26 tables: 12 new + 2 pre-existing (fin_suppliers + fin_supplier_contacts from ADR-051) = 14 total.

06GL Posting + Consumer NestJS Module
Code
Services & Endpoints
  1. PostingService — DOUBLE-ENTRY KEYSTONE. POST /finance/journal-batches (create DRAFT batch with GL entry lines), POST /finance/journal-batches/:id/post (inside one tx: validates period is OPEN, writes all GL entries, calls validate_batch_balance(), flips status to POSTED; RAISE EXCEPTION on imbalance). GET /finance/journal-batches (paginated, filters status + period + source_module), GET /finance/journal-batches/:id (with entries inlined). POST /finance/journal-batches/:id/void (creates a reversing batch with opposite entries; original stays as VOIDED for audit).
  2. GLConsumer — KAFKA CONSUMER KEYSTONE. Subscribes to dev.pay.payment.received, dev.pay.invoice.created, dev.pay.refund.issued, dev.pay.credit_note.issued, dev.pay.debt.written_off. Per event: resolves the school's chart of accounts mapping, constructs a balanced journal batch (e.g., payment received: DEBIT Cash + CREDIT Revenue), calls PostingService.post(). source_event_id UNIQUE provides idempotency — redelivered events are silently skipped. Also updates fin_budget_lines.actual_amount when the posted account maps to a budget line.
Produces → 2 services (1 API + 1 Kafka consumer), ~6 endpoints, 1 new Kafka consumer (GLConsumer on 5 pay.* topics). The first Kafka consumer that writes financial data.
