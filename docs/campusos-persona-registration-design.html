CampusOS|Design Hub|PERSONA & REGISTRATION DESIGN

Persona, Registration & Child Management

How users register, discover their personas, manage children, link canonical accounts, and switch active context in the UI. Prerequisite for enrolment, billing, messaging, and every persona-gated workflow.

Core Principle

CampusOS never asks "what are you?" at registration. A person registers as a person. Personas are discovered through actions: add a child → parent, accept an offer → employee, graduate → alumni, register availability → substitute. The system derives what you are from what you do.

What's new

platform_family_children (new table)

Represents a child within a family. The child may or may not have a canonical iam_person account. This is the parent's view of their children before any school relationship exists.

CREATE TABLE IF NOT EXISTS platform.platform_family_children (
  id              UUID PRIMARY KEY,           -- UUIDv7
  family_id       UUID NOT NULL REFERENCES platform.platform_families(id),
  person_id       UUID REFERENCES platform.iam_person(id),  -- NULL = placeholder
  first_name      TEXT NOT NULL,              -- always set (for display)
  last_name       TEXT NOT NULL,
  date_of_birth   DATE,
  gender          TEXT,
  status          TEXT NOT NULL DEFAULT 'PLACEHOLDER'
                    CHECK (status IN ('PLACEHOLDER','PENDING_LINK','LINKED')),
  invite_code     TEXT,                       -- 8-char code for account linking
  invite_email    TEXT,                       -- where to send the link invite
  invite_sent_at  TIMESTAMPTZ,
  linked_at       TIMESTAMPTZ,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at      TIMESTAMPTZ,
  UNIQUE (family_id, person_id)               -- one link per child per family
);

platform_personas (new table)

Tracks which personas a person holds. Derived from data projections but cached here for fast lookup by /auth/me.

CREATE TABLE IF NOT EXISTS platform.platform_personas (
  id          UUID PRIMARY KEY,
  person_id   UUID NOT NULL REFERENCES platform.iam_person(id),
  type        TEXT NOT NULL
                CHECK (type IN ('PARENT','STUDENT','STAFF','SUBSTITUTE','ALUMNI','COMMUNITY')),
  school_id   UUID REFERENCES platform.schools(id),  -- NULL for platform-wide personas
  label       TEXT NOT NULL,                -- display label ("Teacher at Lincoln Elementary")
  is_active   BOOLEAN NOT NULL DEFAULT true,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (person_id, type, COALESCE(school_id, '00000000-0000-0000-0000-000000000000'::uuid))
);

2. Registration Flow

Registration creates a canonical account. No persona assignment yet — that comes from subsequent actions.

Step 1 — Sign up
User visits /register. Provides: first name, last name, email, phone (optional). CampusOS creates:
• iam_person row (canonical identity)
• platform_users row (auth credentials via Keycloak OIDC)
• platform_families row (every person gets a family unit — even singles)
No persona assigned. No school linked.
Step 2 — Email verification
Standard email verification flow via Keycloak. Until verified, the user can access the "Getting Started" page but cannot perform platform actions.
Step 3 — Getting Started page
After login, if the user has zero personas, they land on /getting-started instead of the launchpad. This page offers action cards:
  • "I have children" → Add children flow (Section 3)
  • "I received an invitation" → Enter invite code → Accept position/link (Section 5)
  • "I want to substitute teach" → Sub profile registration
  • "I'm looking for a school" → Public school finder → Enrolment application
The page disappears once the user has at least one persona. They can always return via settings.

3. Adding Children (Pre-School)

A parent adds children to their family before any school relationship. This is the parent's private family record. The child may or may not have a CampusOS account.

Add child flow

Step 1 — Basic info
Parent provides: first name, last name, date of birth, gender (optional).
Creates a platform_family_children row with status=PLACEHOLDER, person_id=NULL.
Step 2 — Does this child have a CampusOS account?
Three options:

A) "No — they don't have an account yet"
Child stays as PLACEHOLDER. Parent can proceed with browsing schools, but cannot submit an enrolment application until the child is linked to a canonical account. The UI shows a yellow badge: "Account needed for enrolment".

B) "Yes — I have their link code"
Parent enters the child's 8-character link code. The system looks up the code, finds the iam_person, and links:
• Sets person_id on the family_children row
• Sets status=LINKED, linked_at=now()
• Creates a platform_personas row for the parent (type=PARENT) if not already present
The parent persona activates immediately.

C) "I want to create an account for them"
For young children who won't manage their own account. Parent provides an email (or skips email for under-13). The system creates:
• iam_person row for the child
• platform_users row (parent-managed, flagged as minor account)
• Links the family_children row: person_id set, status=LINKED
• Creates parent persona if not present
For under-13 accounts, the parent is the account manager (COPPA/FERPA compliance).

Step 3 — Send a link invitation (optional)
If the child is a PLACEHOLDER and the parent knows their email:
• Parent enters the child's email address
• System generates an 8-character invite_code and sends an email: "Your parent [name] wants to link your CampusOS account to their family. Enter this code in your profile: ABCD-1234"
• Status changes to PENDING_LINK
• When the child (or their other parent) enters the code on their own account, the link completes → LINKED

Accepting a link code (child's side)

The child (or their other parent/guardian) goes to /settings/family and clicks "Link to a family". They enter the 8-character code. The system:
• Validates the code exists and is not expired (72-hour TTL)
• Sets person_id on the platform_family_children row
• Sets status=LINKED
• Creates the PARENT persona for the inviting parent if not present
• Optionally creates a reciprocal family_children row for the child's family (so the child sees the parent too)

Enrolment gate

The enrolment application form (/enrolment/apply) requires the child to be in LINKED status. If the child is PLACEHOLDER or PENDING_LINK, the form shows: "This child needs a CampusOS account before you can apply. [Create account] [Send link invitation]". This ensures the school always receives an application tied to a real canonical identity.

Persona resolution service

API PersonaResolutionService.resolveForPerson(personId)

Queries all projection tables and returns the complete persona set. Called on login, on persona-changing actions, and cached in platform_personas.

async resolveForPerson(personId: string): Promise<Persona[]> {
  const personas: Persona[] = [];

  // PARENT: has any LINKED children in platform_family_children
  const linkedChildren = await this.countLinkedChildren(personId);
  if (linkedChildren > 0) {
    // Find schools where children are enrolled for school-specific parent personas
    const childSchools = await this.getChildSchools(personId);
    for (const school of childSchools) {
      personas.push({ type: 'PARENT', schoolId: school.id, label: `Parent at ${school.name}` });
    }
    if (childSchools.length === 0) {
      // Parent with linked children but no school enrolment yet
      personas.push({ type: 'PARENT', schoolId: null, label: 'Parent' });
    }
  }

  // STAFF: has hr_employees row(s)
  const employments = await this.getActiveEmployments(personId);
  for (const emp of employments) {
    personas.push({ type: 'STAFF', schoolId: emp.schoolId, label: `${emp.jobTitle} at ${emp.schoolName}` });
  }

  // STUDENT: has sis_students row(s) via platform_students
  const enrolments = await this.getActiveEnrolments(personId);
  for (const enr of enrolments) {
    personas.push({ type: 'STUDENT', schoolId: enr.schoolId, label: `Student at ${enr.schoolName}` });
  }

  // SUBSTITUTE: has sub_profiles row
  const subProfile = await this.getSubProfile(personId);
  if (subProfile) {
    personas.push({ type: 'SUBSTITUTE', schoolId: null, label: 'Substitute Teacher' });
  }

  // ALUMNI: has alm_profiles row(s)
  const alumniProfiles = await this.getAlumniProfiles(personId);
  for (const alm of alumniProfiles) {
    personas.push({ type: 'ALUMNI', schoolId: alm.schoolId, label: `Alumni — ${alm.schoolName} ${alm.gradYear}` });
  }

  return personas;
}

5. Invitation & Linking Flows

A. Employee invitation

School admin creates a position offer in /hr/recruitment.
System generates a unique invite token and emails the candidate.
Candidate clicks the link → lands on /invitations/accept?token=xxx.
If they don't have a CampusOS account → redirected to /register with token preserved.
After registration (or login), the invitation page shows position details.
Candidate clicks "Accept" →
• hr_employees row created
• iam_role_assignment granted for the position's role
• platform_personas row: type=STAFF, school=hiring school
• Redirect to launchpad with STAFF persona active

B. Child account linking

Parent A adds a child as PLACEHOLDER → requests link → enters child's email.
System generates 8-char invite_code, emails it to the child (or Parent B).
Child/Parent B logs in → goes to /settings/family → "Enter link code" → enters code.
System validates → links platform_family_children.person_id → status=LINKED.
Both Parent A and the child now see each other in their family view.

C. Student-to-parent linking (school-initiated)

School already has the student enrolled. School admin goes to the student's profile → "Invite parent/guardian".
Enters parent email → system generates invite.
Parent receives email → registers or logs in → accepts →
• sis_student_guardians row created with custody arrangement
• platform_family_children row created (LINKED, since both accounts exist)
• PARENT persona activated

6. Persona Switcher (UI)

Top bar component

WEB A pill/dropdown in the top bar showing the active persona. Clicking opens a menu of all available personas.

DECISION — Persona switcher behaviour

  • Location: Top bar, between the search icon and the notification bell. Shows: persona icon + label (e.g. 👩‍🏫 "Teacher at Lincoln Elementary").
  • Dropdown: Lists all personas. Grouped by type. Active persona has a checkmark.
  • On switch: Frontend calls POST /auth/switch-persona → API returns new permission set → app grid, sidebar, and badge counts refresh → current page reloads if it's persona-specific.
  • Persistence: Active persona stored in localStorage as activePersonaId. On login, if stored persona still exists, resume it. Otherwise default to the first persona.
  • Cross-school switching: If a persona has a schoolId, switching to it also switches the active school context (changes X-Tenant-Subdomain header).

7. Permission Model Changes

UI filtering vs API enforcement

Phase 1 (now): Persona switching only filters the UI. The API returns permissions scoped to the active persona's role assignments. The backend PermissionGuard continues to check full permissions — if a parent somehow hits a teacher-only endpoint, the permission check still denies it because the parent doesn't hold that permission code.

Phase 2 (later): Optional server-side persona enforcement — the API only evaluates permissions for the active persona's role assignments, not the union of all roles. This is stricter but requires session-state management on the server.

How permission filtering works

When a user switches persona, the API resolves permissions for only the role assignments associated with that persona:

  • STAFF persona at School A → permissions from role assignments where scope = School A
  • PARENT persona at School A → permissions from the "Parent" role (stu-001:read, pay-001:read, etc.)
  • Switching to PARENT hides teacher permissions from the response, so the frontend never shows teacher apps
  • The backend guard still works on the full permission set as a safety net

9. Scenarios Walkthrough

Scenario A — New parent with two children

  1. Maria visits /register. Creates account. Lands on Getting Started.
  2. Clicks "I have children". Adds "Sofia, age 14" and "Lucas, age 8".
  3. Both children are PLACEHOLDER. Maria sees them in /family with yellow badges.
  4. Sofia already has a CampusOS account (from a previous school). Maria clicks "Send link invitation" → enters Sofia's email. Status → PENDING_LINK.
  5. Sofia gets email, logs into her account, enters the code at /settings/family. Status → LINKED. Maria's PARENT persona activates.
  6. Lucas is 8 — Maria clicks "Create account for them". System creates Lucas's account (minor, parent-managed). Status → LINKED.
  7. Maria now has two LINKED children. She can browse schools and submit enrolment applications for both.
  8. Maria's launchpad shows parent apps: My Children, Billing, Conferences, Messaging.

Scenario B — Teacher who is also a parent

  1. James Rivera is already registered as a teacher at Lincoln Elementary (STAFF persona).
  2. His daughter Maya is enrolled at the same school. The school admin links James as Maya's parent.
  3. James now has two personas: STAFF (Teacher) + PARENT.
  4. The top bar shows "👩‍🏫 Teacher at Lincoln Elementary" with a dropdown arrow.
  5. James clicks the dropdown, selects "👨‍👧 Parent at Lincoln Elementary".
  6. The launchpad switches from teacher apps to parent apps. James sees Maya's grades, billing, conferences.
  7. James switches back to Teacher to enter grades for his own class.

Scenario C — Student graduates, becomes alumni

  1. Maya Chen is a student at Lincoln Elementary. She has a STUDENT persona.
  2. Maya graduates. The graduation process creates an alm_profiles row.
  3. PersonaResolutionService detects the new alumni profile.
  4. Maya now has: STUDENT (inactive/graduated) + ALUMNI.
  5. Maya's launchpad shows alumni apps: Alumni Network, Events, Giving.

Scenario D — Substitute registers

  1. Alex visits /register. Creates account. Lands on Getting Started.
  2. Clicks "I want to substitute teach". Fills out sub profile (qualifications, availability, schools of interest).
  3. SUBSTITUTE persona activates. Alex sees: Available Assignments, My Schedule, Credentials.
  4. Alex gets assigned to Lincoln Elementary for a day. While there, Alex can access classroom tools for the assigned class only (time-scoped, class-scoped permissions).
