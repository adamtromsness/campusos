CampusOS · Phase 3 Roadmap

Infrastructure, Integration & Ecosystem

Phase 1 built the foundation (34 cycles, 418 tables). Phase 2 builds the depth (30 cycles, 422 tables). Phase 3 is a fundamentally different kind of work — not more tables, but live service deployment, real-world integrations, compliance certification, mobile native apps, and the marketplace ecosystem that transforms CampusOS from a product into a platform. Four themes, fifteen projects, twelve months.
May 2026 · 4 Themes · 15 Projects · ~35 New Tables · 6 Extracted Services · 2 Native Apps · Target: Q3 2027
How Phase 3 Differs from Phases 1 & 2

Phases 1 and 2 are schema-driven: the ERD defines the work, Claude Code builds it cycle by cycle, ChatGPT reviews, human accepts. The build pattern is sequential and the deliverable is code committed to a monolith. Phase 3 breaks that pattern in three ways. First, it's infrastructure-heavy: deploying 6 extracted services requires Terraform, Docker, scaling policies, health checks, and real DevOps — not more NestJS modules. Second, it's integration-heavy: connecting to Jamf, Stripe Connect, PowerSchool, Google Classroom, Ed-Fi, and NSLP APIs requires API keys, sandbox environments, vendor relationships, and data mapping that AI can't do autonomously. Third, it's parallel: with a team of 7–11 (per the business strategy's Month 15–24 hiring plan), multiple projects run simultaneously across different engineers. The CIO orchestrates; no single AI agent owns the full surface.

Theme A — Extracted Service Go-Live

Theme A — Infrastructure

Deploy the 6 Extracted Services for Real

Phases 1 and 2 stubbed all 6 extracted services behind Kafka contracts. Every event envelope, every consumer, every topic ownership is already wired. Phase 3 deploys the real services: separate Docker images, separate Terraform modules, separate scaling policies, separate health checks. No new tables — the schema contracts are already in place. The work is infrastructure + ML pipeline + GPU provisioning.

P3-A1AI Inference Service
Infrastructure

The AI Gateway per ADR-004. Serves all AI workloads: tutoring conversations (P2-7c), learning signal extraction, lesson summary generation, grading assistance, moderation sensitivity scoring (P2-19b), message translation (P2-19a), and future behaviour pattern detection. Deployed as a separate ECS service with GPU instances (or Bedrock/OpenAI API proxy with fallback). PII masking middleware strips student identifiers before prompts reach the model. Per-tenant quota enforcement via Redis counters (cls_ai_usage_log). Rate limiting + cost management + model version pinning.

Deliverables: Terraform module (ECS Fargate + optional GPU), Docker image, PII masking middleware, model router (Claude/GPT-4 configurable per tenant), quota enforcement, health check, Prometheus metrics, Grafana dashboard. Swap all AI stubs in the monolith to real AI Gateway calls.

Depends on: P2-7c (AI tutoring stubs), P2-19a/b (translation + moderation stubs). Unblocks: P3-D4 (behaviour pattern detection AI).
P3-A2Video Processing Service
Infrastructure

GPU workloads for lesson recording transcription (P2-7c cls_lesson_recordings), athletic game streaming (P2-8b ath_game_streams), and highlight clip extraction (P2-8b ath_highlight_clips). Consumes video.uploaded events, processes via FFmpeg + Whisper (or AWS Transcribe), produces video.transcribed events. S3 lifecycle management for raw uploads (hot 30 days, Glacier after 90). Separate from the monolith because GPU workloads cannot share a JVM heap with OLTP traffic.

Deliverables: ECS task definition with GPU, FFmpeg pipeline, transcription integration (Whisper self-hosted or AWS Transcribe), S3 lifecycle policies, dead letter queue for failed processing, retry with exponential backoff.

Depends on: P2-7c (lesson video stubs), P2-8b (streaming stubs). Unblocks: Live lesson transcription, real-time athletic streaming.
P3-A3Notification / Push Service
Infrastructure

Fan-out to thousands of recipients for broadcasts, emergency alerts, and push notifications. Currently the Communications module emits events but delivery is stubbed. This service handles: email delivery (SES/SendGrid with bounce handling), SMS delivery (Twilio/SNS), push notification delivery (FCM + APNs via P2-19b msg_push_device_tokens), WebSocket connections for real-time in-app notifications, and delivery webhook processing for broadcast analytics (P2-19a msg_broadcast_analytics). Redis pub/sub backbone for WebSocket fan-out.

Deliverables: ECS service, email provider integration (SES), SMS provider integration (Twilio), push gateway integration (FCM + APNs), WebSocket server, delivery webhook processor, bounce/complaint handling, unsubscribe management.

Depends on: P2-19a/b (broadcast analytics + push campaigns). Unblocks: Real email/SMS/push delivery, parent bus arrival notifications.
P3-A4Scheduling Solver Service
Infrastructure

Stateless constraint solver (OR-Tools CP-SAT for ≤300 sections, heuristic for >300 per ADR-060). Currently the SchedulingWorker in P2-17a accepts manual candidate creation as fallback. This service receives the constraint payload (teachers, rooms, periods, classes, hard/soft constraints) and returns candidate timetable solutions with clash reports. Deployed as a Python ECS task (OR-Tools is Python-native). Stateless — no database access, pure computation. Timeout: 5 minutes for CP-SAT, 30 seconds for heuristic.

Deliverables: Python Docker image with OR-Tools, gRPC API (constraint payload → candidate solutions), timeout management, solver seed for heuristic reproducibility, Prometheus metrics (solve time, constraint satisfaction rate).

Depends on: P2-17a (scheduling generation stubs). Unblocks: Automated timetable generation for pilot schools.
P3-A5Transport Dispatch Service
Infrastructure

GPS position ingestion from bus fleet (10–30 second intervals per vehicle), ETA computation from position + route geometry + historical speed, and geofence boundary detection. Currently P2-11c accepts manual position entry. This service ingests from GPS hardware providers (Samsara, Verizon Connect, or generic NMEA/GTFS-RT feeds), writes to trn_vehicle_positions (high-volume partitioned table), computes ETAs, checks geofences, and emits parent notification events when bus enters school zone.

Deliverables: ECS service, GPS provider adapter (Samsara API + generic GTFS-RT), position ingestion pipeline (batch insert every 10s), ETA computation engine, geofence check on each position batch, parent tracking token endpoint proxy.

Depends on: P2-11c (GPS telemetry stubs). Unblocks: Real-time parent bus tracking, geofence notifications.
P3-A6Emergency Alert Service
Infrastructure

Crash-recoverable emergency alert fan-out from P2-2's atomic outbox pattern. Currently the Emergency Declaration worker runs in-process. This extracted service guarantees: alert delivery within 60 seconds to all staff + parents, crash recovery (if the service restarts mid-fan-out, it resumes from the last checkpoint), 5-minute PAGE to on-call if any alert stalls, and multi-channel delivery (push + SMS + email simultaneously). The SLA justifies a dedicated service — emergency alerts cannot compete with routine notification traffic.

Deliverables: ECS service with auto-scaling on alert volume, checkpoint-based fan-out, multi-channel parallel delivery, PagerDuty integration for stall detection, delivery confirmation tracking, 99.99% availability target.

Depends on: P2-2 (emergency outbox), P3-A3 (notification service for email/SMS/push). Unblocks: Production emergency drill SLA compliance.

Theme B — Full Finance & Accounting

Theme B — Schema + Logic

M83 Finance + Advanced Procurement

The architecture review (ADR-058) explicitly deferred M83 to post-pilot because double-entry accounting with period close, audit trail, and regulatory reporting is the most complex business logic in the entire system. Phase 2 built the minimal GL backbone (Cycle 26) and the payment flows that post to it. Phase 3 builds the complete finance module and upgrades procurement from basic to full.

P3-B1Full Chart of Accounts + GL + Period Close
Schema

Complete chart of accounts management with account hierarchies (asset, liability, equity, revenue, expense), departmental budgets with encumbrance accounting (budget commitment reduces available balance before payment), period open/close workflow with trial balance verification, year-end close with retained earnings rollforward, and financial statement generation (balance sheet, income statement, cash flow). ~9 tables already in the ERD for M83. The GL backbone from Cycle 26 is the foundation — this adds the full accounting workflow around it.

Deliverables: Chart of accounts CRUD with hierarchy, budget management with encumbrance, period open/close state machine, trial balance computation, year-end close procedure, financial statement PDF generation, audit trail for all GL mutations.

Depends on: Cycle 26 (GL backbone), P2-6 (payment ledger entries). Unblocks: P3-B2 (AP + grants), district-level consolidated financials.
P3-B2Accounts Payable + Grants + Advanced Procurement
Schema

Three-way matching (PO → receipt → vendor invoice with tolerance thresholds), blanket purchase orders for recurring procurement, catalogue-based purchasing with approved vendor catalogues, competitive bidding workflow for high-value purchases, contract lifecycle management, grant tracking with restricted fund accounting (grant funds can only be spent on approved categories), and grant reporting with expenditure vs budget tracking. All deferred by ADR-061 to "post-M83."

Deliverables: Three-way matching engine, blanket PO management, vendor catalogue, bid workflow, contract management, grant fund tracking with restricted spending rules, grant reporting.

Depends on: P3-B1 (full GL + encumbrance). Unblocks: Federal/state grant compliance for US schools, district-level procurement.

Theme C — Compliance & Multi-Region

Theme C — Compliance

DPO Compliance Suite + EU/UK Deployment

13 dpo_ tables already in the ERD. This theme builds the compliance tooling that enables international deployment: GDPR subject access requests, right to erasure, consent management, data processing agreements, breach notification, data retention, and legal holds. Multi-region deployment follows because you can't serve EU/UK schools without GDPR tooling operational. Architecture Review Section 21 defines the multi-region strategy.

P3-C1DPO Compliance Suite
ComplianceSchema

13 new dpo_ tables. Subject access requests (SAR) with automated data assembly across all modules — the DPO clicks "Generate SAR Response" and the system crawls every module's tables for the requested person's data, assembles a PDF, and logs the response. Right to erasure with the pseudonymisation log (ADR-059) — personal data is replaced with pseudonyms across all tables, the pseudonymisation_log records what was erased, and the erasure is irreversible. Consent management with granular per-purpose tracking (marketing, analytics, AI tutoring, photo sharing). Data processing agreements between the school (controller) and CampusOS (processor). Breach notification workflow with GDPR 72-hour regulatory timeline enforcement. Data retention policies with automated purge scheduling (e.g., student records 7 years after graduation). Legal hold management (freezes purge for specific records under litigation).

Deliverables: 13 tables, SAR assembly engine, erasure workflow with pseudonymisation, consent management UI, breach notification timeline tracker, retention policy engine, legal hold freeze mechanism.

Depends on: Phase 2 complete (all modules must exist for SAR assembly to crawl them). Unblocks: P3-C2 (multi-region), EU/UK school sales.
P3-C2Multi-Region Deployment (EU/UK)
Infrastructure

Architecture Review Section 21: EU data residency requires data to stay within the EU region. Terraform modules for eu-west-1 (Ireland) and eu-west-2 (London) deployment. Regional RDS instances with no cross-region replication of PII. Kafka cross-region replication for event idempotency records (platform_event_consumer_idempotency). CloudFront distribution restricted to not cache PII content outside the residency region. Auth0/Cognito regional tenant pools. DNS-based routing (eu.campusos.com vs us.campusos.com). Platform schema (CRM, officials, substitutes, community exchange) replicated globally; tenant schemas regional.

Deliverables: Terraform modules for EU regions, regional RDS provisioning, Kafka cross-region setup, CloudFront geo-restriction, DNS routing, regional auth pools, data residency verification tests.

Depends on: P3-C1 (DPO compliance must be operational before EU deployment). Unblocks: UK independent school market, EU international school market.

Theme D — Integration & Ecosystem

Theme D — Ecosystem

Third-Party Integrations + Mobile + Marketplace

The "last mile" that transforms CampusOS from a standalone product into an ecosystem. Live vendor integrations, native mobile apps, and the marketplace launch. This theme generates direct revenue (marketplace commission, premium integrations) and is the primary driver of competitive differentiation. Most projects can run in parallel across the growing team.

P3-D1SIS Data Import & Migration Toolkit
Integration

Automated data import from the 5 most common US SIS platforms: PowerSchool, Infinite Campus, Skyward, Tyler SIS, and Alma. Each adapter maps the source system's schema to CampusOS's ERD: students → sis_students, guardians → sis_student_guardians, classes → sis_classes, grades → cls_grades, attendance → att_records, staff → hr_employees. Includes a dry-run mode (import to staging, generate diff report, human approves before production write), rollback capability, and duplicate detection (match on name + DOB + school). This is the single biggest friction reducer for pilot onboarding — currently "~2-3 days per school" per the cloud deployment guide; target: <4 hours with the toolkit.

Deliverables: 5 source adapters, schema mapping engine, dry-run + diff report, duplicate detection, rollback, CLI tool + web UI for admins.

Depends on: Phase 2 complete (all target tables must exist). Unblocks: Faster pilot onboarding, self-service school migration.
P3-D2MDM Provider Integration (Jamf / Intune / Mosyle)
Integration

Live MDM API integration replacing the manual status updates in P2-20. Jamf Pro API for Apple device management, Microsoft Intune Graph API for Windows/Chromebook, Mosyle API as a third option. Real remote actions (LOCK, WIPE, RESTART, LOCATE) execute via the MDM provider's API and callback updates tech_remote_actions.status. Device usage summaries (tech_device_usage_summaries) sync nightly from the MDM's app usage reports. Device inventory (tech_assets) auto-sync from MDM enrollment data. Each provider is an adapter behind a common interface — schools configure which MDM they use.

Deliverables: MDM adapter interface, Jamf adapter, Intune adapter, Mosyle adapter, remote action execution + callback, usage sync worker, inventory sync worker, provider configuration UI.

Depends on: P2-20 (IT Advanced stubs). Unblocks: Real device management from within CampusOS.
P3-D3LMS Sync (Google Classroom + Canvas)
Integration

Bidirectional sync with Google Classroom and Canvas LMS. Roster sync: CampusOS sis_classes → Google Classroom courses (or Canvas courses). Assignment sync: cls_assignments ↔ Google Classroom coursework / Canvas assignments. Grade sync: cls_grades ↔ external gradebook. Attendance sync: att_records → external attendance (one-way, CampusOS is source of truth). Schools choose: CampusOS-primary (sync out) or LMS-primary (sync in) per data type. Conflict resolution: last-write-wins with audit log. OAuth2 consent flow for teacher-level authorization.

Deliverables: Google Classroom adapter (REST API), Canvas adapter (REST API), roster sync worker, assignment sync worker, grade sync worker, conflict resolution engine, OAuth2 consent UI, sync status dashboard.

Depends on: Cycle 1 (SIS), Cycle 2 (Classroom), Cycle 3 (Attendance). Unblocks: Schools that can't fully migrate from Google Classroom / Canvas immediately.
P3-D4State Reporting & Ed-Fi / NSLP Integration
IntegrationCompliance

US state reporting format export: Ed-Fi API integration for student demographics, enrollment, attendance, grades, and assessment data. SIF (Schools Interoperability Framework) export for states that require it. NSLP (National School Lunch Program) eligibility verification API integration for P2-10's fds_eligibility_applications — currently manual determination, this automates via the USDA's verification system. State immunisation registry reporting integration for P2-3's health compliance data. Each state has slightly different requirements; start with Kansas (home state), Texas, California, New York as the first four.

Deliverables: Ed-Fi API adapter, SIF export engine, NSLP verification API integration, state immunisation registry adapter (4 states), configurable per-state reporting profiles.

Depends on: P2-3 (health), P2-10 (food service), P2-13 (SIS advanced). Unblocks: District-level sales (districts require state reporting compliance).
P3-D5Native Mobile Apps (Parent + Staff)
Mobile

React Native apps for iOS and Android. Two apps: CampusOS Parent (bus tracking with live map, lunch account balance + deposit, attendance notifications, positive behaviour points, event tickets with QR display, report card viewing, parent-teacher conference booking, emergency alerts) and CampusOS Staff (attendance marking, hall pass management, substitute job acceptance, gate scanning camera, classroom moments photo upload, dispatch event logging). Both apps authenticate via the same Auth0/Cognito flow as the web app. Push notifications via FCM + APNs (wired to P3-A3 Notification Service). Offline mode for attendance marking (sync on reconnect).

Deliverables: React Native monorepo, Parent app (iOS + Android), Staff app (iOS + Android), offline-first attendance, push notification integration, App Store + Play Store submission, MDM distribution profile for staff app.

Depends on: P3-A3 (push notification service), P2-19b (device tokens). Unblocks: Parent engagement (the #1 requested feature from pilot schools).
P3-D6Marketplace & Teacher Content Store Launch
Integration

The Community Exchange (P2-21c) goes live for real transactions. Stripe Connect integration for school-to-school asset settlement (5% platform fee, per the business strategy). Teacher content marketplace with the 20/10/70 revenue split (20% CampusOS, 10% school, 70% teacher). Stripe Connected Accounts for teachers + schools. Payout scheduling (monthly). Tax document generation (1099-K for US teachers earning >$600). Content moderation for marketplace listings. Search promotion algorithm (relevance + quality + freshness). Featured listings. Seller analytics dashboard.

Deliverables: Stripe Connect integration (Connected Accounts, payout scheduling, 1099-K generation), content moderation pipeline, search ranking algorithm, seller analytics, featured listings, marketplace terms of service, payment dispute resolution workflow.

Depends on: P2-21c (Community Exchange schema + basic transaction flow). Unblocks: Revenue stream #2 (marketplace commission), teacher content ecosystem.
P3-D7Advanced Payment Integrations
Integration

Stripe ACH / direct debit for automatic payment plan instalment collection (deferred from P2-6). Stripe SetupIntent integration for saved payment method tokenisation (pay_saved_payment_methods schema ready from P2-6). Lunch account auto-replenishment via Stripe when balance drops below threshold. Apple Pay + Google Pay for event ticket purchases (P2-12) and lunch deposits. International payment methods for non-US schools: SEPA (EU), BACS (UK), iDEAL (Netherlands). Automated reconciliation: Stripe webhook → pay_ledger_entries → GL journal (already wired, needs production hardening).

Deliverables: ACH adapter, SetupIntent flow, auto-replenishment worker, Apple/Google Pay integration, SEPA/BACS/iDEAL adapters, reconciliation hardening, payment failure retry logic.

Depends on: P2-6 (payments advanced), P3-B1 (full GL for reconciliation). Unblocks: Automated billing, international school payments.

Infrastructure Cost Estimate

Phase 3 adds significant infrastructure cost above the ~$800–1,200/month Phase 2 baseline (2–3 pilot schools). The 6 extracted services, GPU instances for AI/video, and multi-region deployment drive the increase. Cost per school decreases as the fleet grows.

Monthly AWS Estimate at Scale (10–20 schools)

Monolith API (ECS Fargate): $400–600. RDS Multi-AZ (r6g.xlarge): $600–900. AI Inference Service (Bedrock/OpenAI API pass-through): $500–2,000 (usage-dependent, per-tenant quota caps this). Video Processing (GPU spot instances): $200–500. Notification Service (SES + Twilio): $100–300. Scheduling Solver (spot, burst only): $50–100. Transport Dispatch (continuous): $150–250. Emergency Alert (always-on): $100–150. Kafka (MSK): $300–500. ElastiCache Redis: $150–250. S3 + CloudFront: $200–400. Multi-region (if EU deployed): +60% of above for second region. Total US-only: $2,750–5,950/month. With EU: $4,400–9,500/month.

At 10 schools × $800–2,000/month subscription = $8K–20K revenue vs $3K–6K infrastructure. Healthy margins from day one at the 10-school mark.

What Phase 3 Is Not

Phase 3 is not another 30 sequential build cycles. The ERD is complete after Phase 2 — all 840 tables exist. Phase 3 adds ~35 new tables (DPO compliance + advanced finance), but the majority of the work is infrastructure, integration, and mobile, not schema design. The build pattern shifts from "one AI agent builds sequentially" to "a team of 7–11 works in parallel across themes." Claude Code remains the primary code generator, but human engineers own the infrastructure projects (Terraform, Kubernetes, vendor API integrations) that require credentials, sandbox environments, and real-world testing that AI can't do autonomously.

Phase 3 is also not the end. There's a Phase 4 on the horizon: district federation (multi-school district management with consolidated reporting, cross-school student transfers, district-wide procurement), white-label / OEM (CampusOS as infrastructure for other edtech products), and the API platform (public developer API for third-party integrations). But Phase 4 is a product strategy decision, not an engineering roadmap — it depends on market feedback from pilot schools and early customers.
