CampusOS — Plan-Level Consistency Audit

Claude's review of all 63 cycle plans cross-referenced against ERD v11, Architecture Review, and Function Library. May 2026.

Executive Summary

0 BLOCKING findings. 4 IMPORTANT findings requiring attention before production. 7 ADVISORY findings for Phase 3 consideration. 8 CLEAN confirmations where things are working well. The plan-level architecture is sound — no structural contradictions found across 63 cycles.

Category 1: Cross-Cycle Dependency Chains

CLEAN — Forward dependencies respected

Every Phase 2 cycle correctly references its Phase 1 foundation tables. No cycle plan references a table that hasn't been built in a prior cycle. Verified chains: P2-6 Payments → Cycle 6 pay_invoices; P2-7 Classroom → Cycle 2 cls_submissions; P2-24 Parent Engagement → P2-12 evt_volunteers + Cycle 3 att_records; P2-27 Portfolio → Cycle 24 pfl_portfolios + P2-13 sis_service_learning_hours; P2-29 Commerce → Cycle 26 fin_chart_of_accounts.

ADVISORY — A-01: Circular soft dependency between P2-27 and P2-13

P2-27 Portfolio Advanced's MilestoneAutoCheckWorker subscribes to sis.service_learning.approved and sis.transcript.generated events from P2-13 SIS Advanced. P2-13 was built first, so the events exist. However, if P2-13 is ever rebuilt or refactored, the worker's event subscriptions need to be verified. This is correctly event-driven (not a direct dependency) but the coupling should be documented in both CLAUDE.md entries.

CLEAN — ALTER TABLE operations documented

5 cycles modify existing tables via ALTER: P2-25 (ALTER lib_checkouts ADD class_set_checkout_id), P2-27 (ALTER pfl_portfolio_items ADD section_id), P2-29b (ALTER str_products ADD category_id), P2-7b implied cls_submissions extensions for peer review. All are nullable FK additions — backward compatible, no data migration needed.

Category 2: Kafka Event Contract Audit

IMPORTANT — K-01: Several Kafka emits lack documented consumers

The following events are emitted in cycle plans but no cycle plan documents a consumer for them:

  • eng.conference.booking_open (P2-24) — should be consumed by Communications for parent notification, but no consumer is documented.
  • eng.survey.opened (P2-24) — same: Communications should notify parents.
  • lib.import.completed (P2-25) — no documented consumer. Likely just an observable event, but should be explicitly noted as "no consumer required" or consumed by admin notification.
  • pub.publication.published (P2-26) — the distribution worker is mentioned but it's internal to the module, not a cross-module consumer.
  • trn.parts.low (P2-11a) — should trigger a procurement requisition suggestion, but no Procurement consumer is documented.
  • fds.inventory.low (P2-10a) — same: should trigger procurement, but no consumer documented.

Resolution: Most of these should be consumed by the Communications/Notification module for alerting. The procurement-triggering events (trn.parts.low, fds.inventory.low) should be documented as "future consumer: Procurement auto-requisition" for Phase 3. None are blocking — events with no consumer simply accumulate in Kafka until a consumer is added.

CLEAN — Core financial event chain complete

The M84 → M83 financial event chain is fully documented: pay.invoice.created, pay.payment.received, pay.credit_note.issued, pay.payment.reversed, pay.debt.written_off are all emitted by M84 and consumed by M83's GLConsumer. evt.event.completed → GL revenue posting is also complete.

ADVISORY — K-02: prc.distribution.completed has 8 potential consumers

The ERD documents prc.distribution.completed as consumed by M62, M61, M63, M24, M66, M64, M65, M67 — each creating inventory records. Only some of these modules have advanced inventory tables built (P2-10 Food Service, P2-11 Transportation, P2-18 Facilities). Others (Library, Athletics, IT, Clubs, Store) may not have inventory receipt handlers yet. The consumer list should be verified against actual implementation.

Category 3: Permission Model Coverage

CLEAN — Every cycle plan documents permission assignments

All 29 Phase 2 cycle plans include explicit permission assignments in their seed data steps, mapping to Function Library codes. The three-tier model (View Only, Read/Write, Admin) is consistently applied.

IMPORTANT — P-01: Student-owned data pattern inconsistently enforced

Several cycle plans declare data as "student-owned" (reflections, portfolios, recruiting profiles, resume) but the enforcement mechanism varies:

  • P2-27 reflections: "only the student can write or edit" — needs service-layer check on student_id = authenticated user
  • P2-8b recruiting profiles: "student-owned: only the student (or coach with permission) can edit" — the "or coach" exception should use a delegation pattern, not a role check
  • P2-27 endorsement visibility: "student controls is_visible_on_share" — student can toggle, but can the endorser see the toggle state?

Resolution: Claude Code audit should verify every "student-owned" table has a service-layer guard checking student_id = req.user.personId. The coach delegation exception in recruiting profiles should be verified as using a proper delegation mechanism (not just role === 'COACH').

ADVISORY — P-02: Parent visibility in custody situations

P2-13a introduces sis_family_relationships with custody_arrangement (JOINT, SOLE_A, SOLE_B). Multiple cycle plans mention "parent sees own child's data" but don't specify custody filtering. If custody_arrangement is SOLE_A, should guardian_b see the student's engagement scores (P2-24), college applications (P2-27), or health records? This filtering logic needs to be centralised, not reimplemented per module.

Category 4: IMMUTABLE Table Enforcement

IMPORTANT — I-01: IMMUTABLE enforcement is service-layer only

All 7 IMMUTABLE tables (fin_gl_entries, pay_credit_notes, pay_payment_reversals, pay_lunch_account_balance_transfers, fds_inventory_transactions, pub_publication_versions, svc_referral_activity) are documented as "NO UPDATE, NO DELETE at the service layer." However, the ERD does not specify database-level enforcement (e.g., a BEFORE UPDATE/DELETE trigger that raises an exception). A developer with direct DB access could violate immutability.

Resolution: Add Postgres triggers: CREATE TRIGGER prevent_update BEFORE UPDATE OR DELETE ON [table] FOR EACH ROW EXECUTE FUNCTION raise_immutable_violation(). This should be a Phase 3 hardening task if not already implemented.

CLEAN — Revert pattern correctly uses append-only

P2-26 pub_publication_versions uses the correct append-only revert pattern: "revert creates NEW version from old snapshot, never modifies existing." This is architecturally sound and the trigger type REVERT properly documents the action.

Category 5: Data Model Concerns

IMPORTANT — D-01: JSONB vs normalised table choices inconsistent

The ERD mixes JSONB columns and normalised tables for similar use cases:

  • JSONB (harder to query): pfl_student_pathway_assignments.milestone_statuses, eng_conference_bookings.follow_up_actions, acc_improvement_action_plans.actions, ext_elections.eligible_voters_filter
  • Normalised (easier to query): pfl_pathway_milestones (separate table for milestone definitions), ext_budget_transactions (separate table for budget entries)

The milestone_statuses JSONB is the most concerning: querying "which students have milestone X completed?" requires a JSONB path query across all assignments. If the readiness dashboard needs to show school-wide milestone completion rates, this will be slow.

Resolution: Consider adding a materialised view or a normalised junction table (pfl_student_milestone_statuses) alongside the JSONB for queryability. The JSONB can remain as the source of truth for the student's full checklist view.

ADVISORY — D-02: TEXT CHECK constraints vs ENUM

The ERD consistently uses TEXT NOT NULL with CHECK constraints instead of Postgres ENUM types. This is actually the correct choice for CampusOS: CHECK constraints are easier to extend (ALTER TABLE ADD CHECK) than ENUMs (which require a type migration). But it should be documented as a deliberate ADR pattern so future developers don't "fix" it by converting to ENUMs.

ADVISORY — D-03: Engagement score privacy concern

P2-24's eng_family_engagement_scores computes a composite score per family from attendance, communications, conferences, volunteering, and payment data. While configurable weights are good, the score itself could be perceived as surveillance. Schools with access to this data might make admission or scholarship decisions based on engagement scores. Consider: should scores be visible to all admin, or restricted to a specific engagement_admin permission? Should scores be excluded from any data export or state reporting?

Category 6: Scalability Flags

ADVISORY — S-01: Read model materialisation frequency

Multiple cycles define materialised read models with different refresh frequencies:

  • Every minute: ConferenceStatusWorker (P2-24), ScheduledPublishWorker (P2-26)
  • Nightly: GraduationAuditWorker (P2-13), ClassSetOverdueWorker (P2-25), FleetStatusWorker (P2-11c), ContractExpiryWorker (P2-29a), LateFeesWorker (P2-6)
  • Weekly: EngagementScoreWorker (P2-24), LibraryRecommendationWorker (P2-25)
  • Monthly: GroupAnalyticsWorker (P2-28a), ProcurementAnalyticsWorker (P2-29a)
  • Annually: WellbeingLongitudinalWorker (P2-28c)

At scale (100+ schools), the nightly workers all running simultaneously could create a thundering herd on the database. Consider staggering: randomise each tenant's nightly run within a 2-hour window. The every-minute workers are fine — they're just polling, not heavy computation.

ADVISORY — S-02: trn_vehicle_positions partitioning

P2-11c correctly identifies trn_vehicle_positions as the highest-volume table (every 10-30 seconds per vehicle). RANGE partition by day with 7-day hot / 90-day cold is specified. However, for a district with 200 buses, that's ~1.7M rows/day. The plan mentions TimescaleDB hypertable as an option. The Claude Code audit should verify which approach was actually implemented and whether the retention policy (auto-drop old partitions) is configured.

The chain from store orders → family account charge → invoice → payment → GL entry is fully planned across Cycles 17 (Store), 6 (Payments core), P2-6 (Payments advanced), 26 (Finance GL). Event-driven at every boundary.

P2-10b's AllergenAlertConsumer properly replaces the Cycle 20 seed-only sync with live event-driven sync from hlth.allergy_alert.changed. The preorder allergen cross-check uses the synced read model.

Overall Assessment

The CampusOS Phase 2 plan-level architecture is structurally sound. No blocking issues found. The 4 IMPORTANT findings are all implementable fixes (add DB triggers for immutability, add Kafka consumers for orphaned events, verify student-owned guards, consider normalising JSONB milestones). The 7 ADVISORY findings are optimisations for production hardening, not design flaws. The cross-module event-driven architecture follows ADR-057 consistently. Financial integrity patterns are correct. The system is ready for code-level audit.
